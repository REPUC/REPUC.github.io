# Linux 进程管理

本篇主题：Linux 进程管理。从程序与进程、进程与线程、并发与并行等基本概念讲起，介绍进程状态与生命周期，重点讲解 ps、top 等进程监控工具的实战用法、进程信号管理、进程优先级调整、后台进程管理（nohup/screen），最后通过 stress、mpstat、pidstat 工具做平均负载的案例分析实战。

# 1. 进程基本概述

# 1.1 程序与进程

  • 什么是程序：开发编写的源代码，封装为产品，比如微信、钉钉等，都称为程序。
  • 什么是进程：程序运行的过程称为进程，它主要用来控制计算机硬件运行我们的程序。

程序与进程区别：

  • 程序：是数据 + 指令的集合，是一个静态的概念，程序可以长期存在于系统中。
  • 进程：是程序运行的过程，是一个动态的概念，运行过程中系统会有各种指标表示当前运行状态；进程会随程序的终止而销毁，不会永久存在于系统中。

# 1.2 进程与线程

假设需要运行 360 安全卫士程序，会先进行资源申请：系统申请一块内存空间、从硬盘中将代码读取到内存、最后进行其他资源的申请。这个申请资源的过程称为进程（资源单位）。

当运行该进程中的病毒扫描、漏洞查找、垃圾清理等功能时，这些功能称为进程中的线程。线程是运行代码的过程，是一个执行单位，是进程中更细的单位；一个进程有多个线程时，线程之间互不影响，同时多线程之间可以实现数据共享。

工厂流水线例子：工厂（操作系统）→ 进程（车间）→ 线程（流水线作业）。

# 1.3 并发与并行

  • 并发：多个任务看起来是同时运行，这是一种假并行（CPU 在任务中来回切换）。即 CPU 在多个程序之间来回切换。
  • 并行：多个任务是真正的同时运行，并行必须有多核 CPU 才可以实现。即程序同时运行。

# 1.4 进程运行的状态

一般来说，进程有三个状态：就绪状态、运行状态、阻塞状态。

  • 运行态：进程占用 CPU，并在 CPU 上运行
  • 就绪态：进程已经具备运行条件，但需要等待 CPU 的调度才可运行
  • 阻塞态：进程因等待某件事发生而暂时不能运行

三种状态之间转换的几种情况：

  • 运行 → 阻塞：进程发生 I/O 操作，需等待事件而无法继续执行，进程由运行状态变为阻塞状态
  • 阻塞 → 就绪：进程所等待的事件已经完成，但无法直接运行，需要进入就绪队列等待调度
  • 就绪 → 运行：运行的进程时间片已经用完，CPU 会从就绪队列中选择合适的进程分配 CPU
  • 运行 → 就绪：
      1. 进程占用 CPU 的时间过长，而系统分配给该进程占用 CPU 的时间是有限的
      1. 当有更高优先级的进程要运行时，该进程需要让出 CPU，由运行状态转变为就绪状态

# 1.5 进程的生命周期

生命周期指一个对象的生老病死。当父进程接收到任务调度时，会通过 fork 派生子进程来处理，子进程会继承父进程属性：

  1. 子进程处理任务代码时，父进程其实不会进入等待，其运行过程由 Linux 系统进行调度。
  2. 子进程处理任务代码后会执行退出，然后唤醒父进程来回收子进程的资源。
  3. 如果子进程在处理任务过程中异常退出，而父进程没有回收子进程资源，会导致子进程运行实体已经消失，但仍然在内核的进程表中占据一条记录，长期下去对系统资源是一种浪费，这就是僵尸进程。
  4. 如果子进程在处理任务过程中，父进程退出了，子进程没有退出，那么这些子进程就没有父进程来管理了，由系统的 systemd（system 进程，PID 1） 接管管理，这就是孤儿进程。

PS：每个进程都有父进程的 PPID，自己的编号叫 PID。

# 2. 进程运行状态监控

程序运行后，需要了解进程的运行状态。查看进程状态分为：静态查看和动态查看。

# 2.1 静态监控进程 ps

ps -aux 是常用组合，可查看进程的用户、PID、占用 CPU 百分比、占用内存百分比、状态、执行的命令等。

# 2.1.1 每列指标详解

USER       PID %CPU %MEM    VSZ   RSS TTY     STAT START TIME COMMAND
root      1 0.0  0.2 125912 4516 ?     Ss 4月25 0:08 /usr/lib/systemd/systemd --switched-root --system --deserialize 22
root      2 0.0  0.0    0   0 ?     S  4月25 0:00 [kthreadd]
  • USER：启动进程的用户
  • PID：进程运行的 PID 号
  • %CPU：进程占用 CPU 百分比
  • %MEM：进程占用内存百分比
  • VSZ：进程占用虚拟内存大小（单位 KB）
  • RSS：进程占用物理内存实际大小（单位 KB）
  • TTY：进程由哪个终端启动运行，如 tty1、pts/0 等；? 表示内核程序，与终端无关
  • STAT：进程运行过程中的状态（man ps 查看 /STATE）
  • START：进程的启动时间
  • TIME：进程占用 CPU 的总时间（为 0 表示还没有开始运行）
  • COMMAND：程序的运行指令，[ ] 属于内核态进程，没有 [ ] 属于用户态进程

[root@oldwang ~]# cat zombie.py
#!/usr/bin/env python
# encoding: utf-8
from multiprocessing import Process
import time
import os
def task():
    print("子进程ID --> %s" % os.getpid())
    time.sleep(16)
if __name__ == "__main__":
    for i in range(3):
        p = Process(target=task)
        p.start()
        print("父进程ID --> %s" % os.getpid())
    time.sleep(100000)

# 2.3 动态监控进程 top

使用 top 命令可以查看当前进程状态（动态）。

# 2.3.1 top 命令选项

执行 top 时可指定的命令选项：

  • -d：刷新时间
  • -p：指定 PID
  • -u：指定用户

示例用法：

[root@oldwang ~]# top -d 1 -p PID
[root@oldwang ~]# top -d 1 -p $(pgrep nginx)

# 动态查看 oldwang 运行的进程
[root@oldwang ~]# top -d 1 -u oldwang

# 2.3.2 top 内部选项

执行 top 后可使用的内部选项：

  • c：改变 top 刷新频率（一般不建议设定）
  • P：按 CPU 进行排序
  • M：以内存进行排序
  • R：对排序后的结果进行倒序
  • f：自定义显示的字段，比如打印 PPID
  • k：指定杀死某个 PID
  • 1：显示 CPU 核心数
  • z：以高亮显示数据
  • b：高亮显示处于 R 状态的进程

# 2.3.3 top 字段含义

top - 21:48:25 up 1 day, 20:30, 1 user, load average: 0.00, 0.01, 0.05
Tasks: 129 total,   1 running, 128 sleeping,   0 stopped,   0 zombie
%Cpu(s):  0.7 us,  0.7 sy,  0.0 ni, 98.7 id,  0.0 wa, 0.0 hi, 0.0 si, 0.0 st
KiB Mem : 2028088 total,   195468 free,   666536 used, 1166084 buff/cache
KiB Swap: 2097148 total, 1940724 free,   156424 used. 1084200 avail Mem

PID USER     PR NI   VIRT   RES   SHR S %CPU %MEM    TIME+ COMMAND
1083 root      20   0 298628  2808 1544 S  0.3  0.1  2:36.62 vmtoolsd

Tasks 字段含义：

  • 129 total：当前进程的总数
  • 1 running：正在运行的进程数量
  • 128 sleeping：睡眠的进程数量
  • 0 stopped：停止的进程数量
  • 0 zombie：僵尸进程数量

%Cpu(s) 字段含义：

  • us：系统用户进程使用 CPU 百分比
  • sy：内核中的进程占用 CPU 百分比，通常内核负责与硬件交互
  • id：空闲 CPU 的百分比
  • wa：CPU 等待 I/O 完成的时间
  • hi：硬中断，占的 CPU 百分比
  • si：软中断，占的 CPU 百分比
  • st：比如虚拟机占用物理 CPU 的时间

# 2.3.4 如何理解中断

中断是 CPU 处理外部事件的一种机制，分为硬中断（硬件设备触发，如磁盘、网卡）和软中断（内核或进程主动触发，如系统调用、定时任务），top 中的 %hi 和 %si 分别对应两者占用的 CPU 百分比。

# 2.3.5 内存相关命令

查看内存使用一般使用 free 命令，需要了解每列含义及计算公式：

  • total 总内存：used + free + buffer + cache = total
  • used 已使用内存：total - free - buffers - cache = used（含 shared）
  • free 未被使用的内存：total - used - buffer - cache = free
  • available 可获得内存：free + (buffer + cache 可释放的空间) = available
[root@web@1 ~]# free -m
total      used      free     shared buff/cache available
Mem:         972       224       474        79       273       484
Swap:        2047        8      2047

需要注意：

  • free：表示当前完全没有被程序使用的内存
  • cache：在有需要时，是可以被释放出来以供其它进程使用的
  • available：表示系统目前能提供给新应用程序使用的内存

手动释放内存 buffer/cache：

  • 第一步：sync
  • 第二步：echo "3" > /proc/sys/vm/drop_caches

# 3. 管理进程状态

# 4. 进程优先级

# 4.1 什么是进程优先级

优先级指的是优先享受资源，比如排队买票时，军人优先、老人优先等。

# 4.2 为何需要优先级

举例：海底捞火锅正常情况下响应就特别慢，节假日人员突增会导致处理请求特别慢。

  • 假设我是海底捞 VIP 客户（最高优先级），无论多么繁忙，我都无需排队，海底捞人员会直接服务于我，满足我的需求。
  • 如果我不是 VIP 的人员（较低优先级），则进入排队等待状态。

# 4.3 进程如何配置优先级

在启动进程时，为不同的进程使用不同的调度策略：

  • nice 值越高：表示优先级越低，例如 +19，该进程容易将 CPU 使用量让给其他进程
  • nice 值越低：表示优先级越高，例如 -20，该进程不倾向于让出 CPU

# 4.4 进程优先级如何查看

  1. 使用 top 命令查看优先级：

# PR：显示 nice 折算后的优先级，-20 对应 0，+19 对应 39

98417 vim                      -5

# 4.6 修改进程优先级 renice

# 1. 查看当前正在运行的 sshd 进程优先级状态
[root@oldwang ~]# ps axo pid,command,nice | grep [s]shd
70848 sshd: root@pts/2              9
98002 /usr/sbin/sshd -D             9

# 2. 调整 sshd 主进程的优先级
[root@oldwang ~]# renice -n -20 98002
98002 (process ID) old priority 9, new priority -20

# 3. 调整之后需要退出终端，重新打开一个新终端
[root@oldwang ~]# ps axo pid,command,nice | grep [s]shd
70848 sshd: root@pts/2              9
98002 /usr/sbin/sshd -D            -20
[root@oldwang ~]# exit

# 4. 再次登录 sshd 服务，会由主进程 fork 子 sshd 进程（子进程会继承主进程的优先级）
[root@oldwang ~]# ps axo pid,command,nice | grep [s]shd
98002 /usr/sbin/sshd -D            -20
98122 sshd: root@pts/0            -20

# 5. 后台进程管理

# 5.1 什么是后台进程

通常进程都会在终端前台运行，一旦关闭终端，进程也会随之结束。因此希望将前台运行的进程放入后台运行，即使关闭了终端也不影响进程的正常运行。

# 5.2 为什么需要后台运行

例如：从国内服务器往国外服务器传输大文件时，由于网络问题需要传输很久，如果在传输过程中出现网络抖动或不小心关闭了终端，会导致传输失败。如果将传输的进程放入后台，就能解决此类问题。

# 5.3 如何将进程转为后台

早期大家都使用 nohup + & 将进程放入后台，再用 jobs、bg、fg 等方式查看进程状态，但太麻烦也不直观，推荐使用 screen。

# 5.3.1 nohup 方式

# 1. 使用 nohup 将前台进程转换后台运行
[root@oldwang ~]# nohup sleep 3000 &

# 2. 查看进程运行情况
[root@oldwang ~]# ps aux | grep sleep | grep -v grep
root     75118 74766  0 11:10 pts/0   00:00:00 sleep 3000

# 3. 使用 jobs、bg、fg 等方式查看后台作业
[root@oldwang ~]# jobs          # 查看后台作业
[1]+  Running  sleep 3000 &
[root@ansible ~]# fg %1       # 将作业调到前台
[root@ansible ~]# bg %1       # 将作业调到后台

# 5.3.2 screen 方式

# 1. 安装 screen 工具
[root@web ~]# yum install screen -y

# 2. 开启一个 screen 子窗口，可以通过 -S 为其指定名称
[root@web ~]# screen -S wget_soft

# 3. 在 screen 窗口中执行任务，可以执行前台运行的任务

# 4. 平滑退出 screen，但不会终止 screen 中的前台任务（ctrl+a+d）

# 5. 查看当前有多少 screen 正在运行
[root@web ~]# screen -ls
There is a screen on:
22058.wget_soft (Detached)
1 Socket in /var/run/screen/S-root.

# 6. 可以通过 screenid 或 screen 标签名称进入
[root@web ~]# screen -r wget_soft
[root@web ~]# screen -r 22058
[root@web ~]# exit            # 退出 screen，终止任务

# 6. 系统平均负载

每次发现系统变慢时，通常做的第一件事就是执行 top 或 uptime 了解系统的负载情况。

[root@oldwang ~]# uptime
04:49:26 up 2 days, 2:33, 2 users, load average: 0.70, 0.04, 0.05
# 系统时间 运行时长 登录用户数 平均负载（1分钟、5分钟、15分钟）

# 6.1 什么是平均负载

平均负载是单位时间内的 CPU 使用率吗？ 上面的 0.70 代表 CPU 使用率是 70%？其实不是。

平均负载是指单位时间内，系统处于可运行状态和不可中断状态的平均进程数，也就是平均活跃进程数；可以理解为"平均负载"是"单位时间内的活跃进程数"。平均负载与 CPU 使用率并没有直接关系。

# 6.1.1 可运行状态

可运行状态进程：指正在使用 CPU 或正在等待 CPU 的进程，也就是 ps 命令中看到处于 R 状态的进程。

# 6.1.2 不可中断状态

不可中断进程：系统中最常见的是等待硬件设备的 I/O 响应，通过 ps 命令中看到 D（Disk Sleep） 的进程。

例如：当一个进程向磁盘读写数据时，为了保证数据的一致性，在得到磁盘回复前，它不能被其他进程或中断打断，此时进程处于不可中断状态。如果此时进程被打断，就容易出现磁盘数据与进程数据不一致的问题。

所以，不可中断状态实际上是系统对进程和硬件设备的一种保护机制。

# 6.2 平均负载为多少时合理

理想的状态是每个 CPU 上都刚好运行着一个进程，这样每个 CPU 都得到了充分利用。评判平均负载时，首先要知道系统有几个 CPU，可通过 top 命令或 /proc/cpuinfo 获取。

示例：假设在 4、2、1 核的 CPU 上，平均负载为 2 时意味着什么？

    1. 在 4 个 CPU 的系统上，意味着 CPU 有 50% 的空闲
    1. 在 2 个 CPU 的系统上，意味着所有的 CPU 都刚好被完全占用
    1. 在 1 个 CPU 的系统上，则意味着有一半的进程竞争不到 CPU

平均负载有三个数值，应该关注哪个？ 三个指标都需要关注（就好比一天的天气要结合起来看）：

  • 1 分钟、5 分钟、15 分钟的三个值基本相同或相差不大，说明系统负载很平稳
  • 1 分钟的值小于 15 分钟的值，说明系统最近 1 分钟的负载在减少，而过去 15 分钟内却有很大的负载
  • 如果 1 分钟的值远大于 15 分钟的值，说明最近 1 分钟的负载在增加，这种增加可能是临时性的，也可能还会持续上升，需要持续观察
  • 一旦 1 分钟的平均负载接近或超过 CPU 的个数，就意味着系统正在发生过载问题，这时就要分析问题并想办法优化

例：在有 2 个 CPU 的系统上看到平均负载为 2.73、6.98、12.98：

  • 说明在过去 1 分钟内，系统有 136% 的超载（2.73/2=136%）
  • 在过去 5 分钟内，有 345% 的超载（6.98/2=345%）
  • 在过去 15 分钟内，有 649% 的超载（12.98/2=649%）
  • 从整体趋势来看，系统的负载在逐步降低

# 6.4 平均负载与 CPU 使用率

实际工作中经常容易把平均负载和 CPU 使用率混淆，这里做一个区分。既然平均负载代表活跃进程数，那平均负载高了，不就意味着 CPU 使用率高吗？

回到平均负载的含义：平均负载是单位时间内处于可运行状态和不可中断状态的进程数，所以它不仅包括正在使用 CPU 的进程，还包括等待 CPU 和等待 I/O 的进程。而 CPU 使用率是单位时间内 CPU 繁忙情况的统计，与平均负载并不一定完全对应：

  • CPU 密集型进程：使用大量 CPU 计算会导致平均负载升高，此时两者是一致的
  • I/O 密集型进程：等待 I/O 也会导致平均负载升高，但 CPU 使用率不一定很高
  • 大量的 CPU 进程调度：也会导致平均负载升高，此时 CPU 使用率也会比较高

# 6.5 平均负载案例分析实战

演示三种常见场景，用 stress、mpstat、pidstat 等工具找出平均负载升高的根源：

  • stress：Linux 系统压力测试工具，这里用作异常进程模拟平均负载升高的场景
  • mpstat：多核 CPU 性能分析工具，用来实时查看每个 CPU 的性能指标及所有 CPU 的平均指标
  • pidstat：常用的进程性能分析工具，用来实时查看进程的 CPU、Mem、I/O 等性能指标
[root@oldwang ~]# yum install stress sysstat -y

# 6.5.1 场景 1 - CPU 密集型进程

# 1. 第一个终端运行 stress 命令，模拟一个 CPU 使用率 100% 的场景
[root@oldwang ~]# stress --cpu 1 --timeout 600

# 2. 第二个终端运行 uptime 查看平均负载的变化情况
[root@oldwang ~]# watch -d uptime
17:27:44 up 2 days, 3:11, 3 users, load average: 1.10, 0.30, 0.17

# 3. 在第三个终端运行 mpstat 查看 CPU 使用率的变化情况
# -P ALL 查看所有 CPU，每 5 秒输出一组数据
[root@oldwang ~]# mpstat -P ALL 5
Linux 3.10.0-957.1.3.e17.x86_64 (m01)  2019/10/29    _x86_64_  (1 CPU)
17时32分63秒  CPU    %usr %nice    %sys %iowait    %irq %soft %steal %guest %gnice  %idle
17时32分68秒  all  99.80   0.00   0.20   0.00   0.00   0.20   0.00   0.00   0.00    0.00
17时32分68秒   0  99.80   0.00   0.20   0.00   0.00   0.20   0.00   0.00   0.00    0.00
# 可看到该 CPU 的使用率几乎 100%，但 iowait 为 0

# 4. 从终端二可以看到，1 分钟的平均负载会慢慢增加到 1.00，终端三中正好有一个 CPU 使用率 100%，且 iowait 为 0，说明平均负载的升高正是由于 CPU 使用率。到底是哪个进程导致的？使用 pidstat 查询
# 每 5 秒后输出一组数据
[root@oldwang ~]# pidstat -u 5 1
Linux 3.10.0-957.1.3.e17.x86_64 (m01)  2019/10/29    _x86_64_ (1 CPU)
17时33分21秒  UID       PID    %usr %system %guest    %CPU CPU Command
17时33分26秒    0   110019 98.80   0.00   0.00 98.80   - stress
# 发现是 stress 进程，说明该进程占满了 CPU

# 6.5.2 场景 2 - I/O 密集型进程

# 1. 在第一个终端运行 stress 命令，这次模拟 I/O 压力，即不停地执行 sync
[root@oldwang ~]# stress --io 1 --timeout 600

# 2. 在第二个终端运行 uptime 查看平均负载的变化情况
[root@oldwang ~]# watch -d uptime
18:43:51 up 2 days, 4:27, 3 users, load average: 1.12, 0.65, 0.00

# 3. 最后第三个终端运行 mpstat 查看 CPU 使用率的变化情况
# 此时会看到 iowait 比较高，%sys 占用升高
[root@oldwang ~]# mpstat -P ALL 5
Linux 3.10.0-693.2.2.e17.x86_64 (bgx.com)  2019/11/7    _x86_64_   (1 CPU)
14时26分67秒  CPU    %usr %nice    %sys %iowait    %irq %soft %steal %guest %gnice  %idle
14时26分12秒  all   0.20   0.00  82.45  17.35   0.00   6.66   0.00   0.00   0.00    6.66
14时26分12秒   0   0.20   0.00  82.45  17.35   0.00   6.66   0.00   0.00   0.00    6.66

# 4. 因为 iowait 高，需要用 pidstat 来查询
# 每 5 秒输出一组数据，-u 查看 CPU
[root@oldwang ~]# pidstat -u 5 1
Linux 3.10.0-957.1.3.e17.x86_64 (m01)  2019/11/29    _x86_64_ (1 CPU)
18时29分37秒  UID       PID    %usr %system %guest %wait    %CPU CPU Command
18时29分42秒    0   127259 32.60   0.20   0.00  67.20 32.80   - stress

18时29分42秒    0   127262  4.20  28.60   0.00  67.20 32.80   - stress
# 可以发现，还是 stress 进程导致的

# 6.5.3 场景 3 - 大量的进程

# 1. 在第一个终端使用 stress，这次模拟的是 4 个进程
[root@oldwang ~]# stress -c 4 --timeout 600

# 2. 由于系统只有 1 个 CPU，明显比 4 个进程要少得多，系统 CPU 处于严重过载状态
[root@oldwang ~]# watch -d uptime
19:11:07 up 2 days, 4:45, 3 users, load average: 4.65, 2.65, 4.65

# 3. 最后通过 pidstat 查询进程的情况：可以看出 4 个进程在争抢 1 个 CPU，每个进程等待 CPU 的时间（%wait 列）高达 75%，这些超出 CPU 计算能力的进程最终导致 CPU 过载
[root@oldwang ~]# pidstat -u 5 1
平均时间:  UID       PID    %usr %system %guest %wait    %CPU CPU Command
平均时间:    0   136298 24.55   0.00   0.00 75.25 24.55   - stress
平均时间:    0   136291 24.95   0.00   0.00 75.25 24.95   - stress
平均时间:    0   136292 24.95   0.00   0.00 75.25 24.95   - stress
平均时间:    0   136293 24.75   0.00   0.00 74.65 24.75   - stress

# 6.5.4 总结

分析完三个案例，归纳平均负载与 CPU 的关系：

  • 平均负载提供了一个快速查看系统整体性能的手段，反映了整体的负载情况。但只看平均负载本身，并不能直接发现瓶颈在哪里，分析时需要注意：
  • 平均负载高有可能是 CPU 密集型进程导致的
  • 平均负载高并不一定代表 CPU 使用率高，还有可能是 I/O 更繁忙了
  • 当发现负载高时，可以使用 mpstat、pidstat 等工具，辅助分析负载的来源
