# 4.1.2　⭐ 一分钟判定法

面对任何一个要监控的软件，按这个顺序问自己：

第 1 步：curl http://<软件>:<端口>/metrics
         ├─ 有内容  → ① 或 ②，直接在 prometheus.yml 加一个 job 就完事
         └─ 没有    → 第 2 步

第 2 步：搜 "<软件>_exporter"
         ├─ 有官方/社区 Exporter → ③，部署 Exporter
         └─ 没有               → 第 3 步

第 3 步：它是长期运行的服务吗？
         ├─ 是（能改代码）        → ⑤ 自行编程（Instrumentation）
         ├─ 是（不能改代码、纯黑盒）→ 找 Exporter 或 blackbox_exporter
         └─ 不是（跑一下就退出）  → ④ Pushgateway

🧠 为什么先 curl？ 因为这一步直接决定了后面所有的架构选择。
能在浏览器里看到指标，就不需要写代码；看不到，才有必要往下走。

import random
import time

REQUEST_TIME = Summary('request_processing_seconds', 'Time spent processing request')

# 4.2.3　完整案例：一个"带业务指标"的 Flask 应用

#!/usr/bin/python3
from prometheus_client import start_http_server, Counter, Summary
from flask import Flask, jsonify
from wsgiref.simple_server import make_server

app = Flask(__name__)

# ① Summary：统计每次请求的处理耗时（自动生成 _sum / _count / _bucket... ）
REQUEST_TIME = Summary('request_processing_seconds', 'Time spent processing request')

# ② Counter：统计请求总次数（自动生成 request_count_total）
COUNTER_TIME = Counter('request_count', 'Total request count of the host')


@app.route("/metrics")
@REQUEST_TIME.time()          # ← 装饰器自动观测本次调用耗时
def requests_count():
    COUNTER_TIME.inc()        # ← 每次访问，计数 +1
    return jsonify({"return": "success OK!"})


if __name__ == "__main__":
    start_http_server(8000)                                # ③ 指标暴露端口
    httpd = make_server('0.0.0.0', 8001, app)              # ④ 业务访问端口
    httpd.serve_forever()

# 4.2.4　⭐ 为什么开了两个端口？（这是本节最值得理解的点）

端口角色作用
8001业务服务端接收真实访问请求，触发 COUNTER_TIME.inc()
8000指标暴露端点Prometheus 从这里 GET /metrics 抓数据

为什么不合并成一个？

因为这两个端口的访问者完全不同：

  • 8001 面对的是用户/客户端——每来一次真实请求，计数器就 +1；
  • 8000 面对的是Prometheus——它每 10~15 秒来抓一次，这次抓取不应该被当成一次业务请求。

如果合成一个端口，Prometheus 抓数据 这个动作本身就会让计数器 +1，指标就自己污染自己了。

🧠 一句话总结：业务端口计数，指标端口读表。两者的流量必须分开。

💡 这个"双端口"模式在生产里很常见：主业务端口跑业务，另开一个 9090/8000 之类的管理端口专门暴露指标。很多 Java 应用（Spring Boot Actuator）也是这么设计的。

# 4.2.6　制造流量：让指标动起来

手工 curl 太慢，写个循环：

# 简单版：固定频率
while true; do curl -s http://10.0.0.101:8001/metrics > /dev/null; sleep 1; done

# 随机版（更像真实用户，时长快时慢）
while true; do
  curl -s http://10.0.0.100:8001/metrics > /dev/null
  sleep 0.$(shuf -i 1-9 -n 1)
done

再访问一次 8000/metrics，你会看到 request_count_total 已经涨上去了。

# 4.3　Go 定制 Exporter：10 行代码，1 个二进制

Go 是 Prometheus 的原生语言，写 Exporter 更"顺"。

apt update && apt -y install golang
go version
mkdir -p code && cd code

cat > main.go << 'EOF'
package main

import (
    "net/http"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
    // Serve the default Prometheus metrics registry over HTTP on /metrics.
    http.Handle("/metrics", promhttp.Handler())
    http.ListenAndServe(":9527", nil)
}
EOF
# 静态编译（关键！）
export CGO_ENABLED=0
export GOARCH=amd64
export GOOS=linux

go mod init my_metric
go env -w GOPROXY=https://goproxy.cn,direct          # 国内加速
go get github.com/prometheus/client_golang/prometheus/promhttp

go build -o exporter_demo
ldd exporter_demo          # → "不是动态可执行文件"（静态链接）
./exporter_demo &
curl http://127.0.0.1:9527/metrics

📌 两行核心：

  • promhttp.Handler() 直接给你一个"标准的 /metrics 处理器"；
  • http.ListenAndServe(":9527", nil) 把它挂到端口上。

剩下全是业务逻辑。

# 4.4.3　⭐ 三个需求，三条 PromQL

用 4.2 节那个 Flask 应用的指标，做三张图：

# 4.5　标签体系：Prometheus 数据模型的灵魂

# 4.5.1　标签的三类

类型来源例子
默认标签（Prometheus 内置）Prometheus 自己生成，__* 形式__address__、__scheme__、__metrics_path__、__name__
应用标签（软件自带）被监控程序自身的指标里带的维度cpu、mode、device、mountpoint、le、quantile
自定义标签（用户定义）你在配置里加的env: prod、app: k8s-node

# 4.5.2　⭐ 私有标签（__*）全清单

这些是 Prometheus 的"内部变量"，不要自己定义，但必须知道它们的含义。

标签含义默认值
__name__指标名本身指标名
__address__target 的套接字地址<host>:<port>
__scheme__抓取协议http
__metrics_path__指标 URI 路径/metrics
__param_<name>URL 中第一个同名参数的值依赖 URL 是否有参数
__meta_<...>服务发现返回的元数据标签（每种 SD 不同）由 SD 机制填充
__tmp / __tmp_*用户临时存放标签值的保留前缀—

三条铁律：

  1. __ 开头是保留的，用户自定义标签不要用这个前缀；
  2. __ 开头的标签不会被存进 TSDB——它们在 relabel 结束后会被全部移除；
  3. 需要在 relabel 过程中临时保存某个值时，用 __tmp 开头，避免和内置标签冲突。

# 4.5.4　⭐ 一个关键推论：instance 是 __address__ 改出来的

讲师在课堂上发现了一个"看起来很奇怪"的现象：

看 Targets 页面，"原始标签"里有 __address__="10.0.0.101:9100"，但"最终标签"里没有 __address__，却多了一个 instance="10.0.0.101:9100"。

这就是 Prometheus 内置完成的一次标签改写：

__address__  →（改名）→  instance

同理：

job_name（配置里的）  →（添加）→  job="node_exporter"

Prometheus 在 relabel 之前，会为每个 target 自动做这几件事：

  1. 把 job 标签设为配置中 job_name 的值；
  2. 把 __address__ 设为 "<host>:<port>"；
  3. 把 instance 设为 __address__ 的值；
  4. 把 __scheme__ 设为 http/https；
  5. 把 __metrics_path__ 设为 /metrics；
  6. 填充 __param_<name>（如果 URL 有参数）。

🧠 所以你可以这样理解：
Prometheus 在"拿到 target 的那一刻"，就已经做了一次最基础的标签管理。
你在 Targets 页看到的"原始标签 → 最终标签"两栏，就是"relabel 前"和"relabel 后"的对比。这个页面是你调试标签配置的第一现场。

# 4.6　relabel_configs：抓取前，对 target 动手

# 4.6.1　完整语法

scrape_configs:
  - job_name: 'xxx'
    relabel_configs:            # 或 metric_relabel_configs
      - source_labels: [<labelname>, ...]
        separator: '<string>'          # 默认 ";"
        regex: '<regex>'               # 默认 "(.*)"
        replacement: '<string>'        # 默认 "$1"
        target_label: '<labelname>'
        action: '<relabel_action>'     # 默认 "replace"
        modulus: <uint>                # 仅 hashmod 用

# 4.6.2　七个字段的准确含义

字段作用默认值
action执行什么操作。它决定了其他字段怎么被解释replace
source_labels参与运算的源标签列表—
separator多个 source_labels 拼接时的分隔符;
regex对"拼接后的值"或"标签名"做匹配的正则(.*)
replacement替换/赋值时用的新值，支持 $1 $2 反向引用$1
target_label结果写到哪个标签（不存在则新建）—
modulus取模，仅 hashmod 使用（用于分片）—

🧠 理解 replace 的执行顺序，一切就都通了：

1. 取出 source_labels 里各标签的值
2. 用 separator 拼成一个字符串
3. 用这个字符串去匹配 regex
4. 匹配成功 → 按 replacement（可用 $1..$n 引用 regex 分组）算出新值
5. 把新值赋给 target_label
6. 匹配失败 → 什么都不做

# 4.6.3　九种 action

分类action作用
改值replace⭐ 默认。匹配则给 target_label 赋值（不存在就新建）
hashmod把拼接值的 hash 对 modulus 取模后存入 target_label（分片用）
lowercase拼接值转小写
uppercase拼接值转大写
过滤目标/样本keep匹配则保留，不匹配丢弃
drop匹配则丢弃，不匹配保留（与 keep 相反）
改标签名labelmap对标签名做正则，把匹配到的标签复制成新名字（旧标签保留）
labeldrop对标签名做正则，匹配则删除该标签（黑名单）
labelkeep对标签名做正则，匹配则保留，不匹配删除（白名单）

📌 最容易混淆的一点：

  • replace / keep / drop 的 regex 匹配的是标签的"值"（拼接后的值）；
  • labelmap / labeldrop / labelkeep 的 regex 匹配的是**"标签名"**。

一个看值、一个看名——这是本节唯一必须记死的事情。

⚠️ labelmap 有个特别之处：它不会删除旧标签，只是额外生成一个新名字的标签。所以用完之后经常要再配一条 labeldrop 清理旧名——这正是下一节案例 2 + 案例 3 的来历。

# 4.7　metric_relabel_configs：抓取后，对样本动手

# 4.7.1　两兄弟的区别（必须能背）

维度relabel_configsmetric_relabel_configs
执行时机抓取之前（scrape 之前）抓取之后（scrape 之后、入库之前）
操作对象target 本身（主机/端点）target 上的每一条 metric 样本

🧠 一句话记忆：
relabel_configs 管"人"，metric_relabel_configs 管"数据"。
前者决定"要不要监控这台机器"，后者决定"这台机器上的哪些指标留下"。

💡 一个重要细节：metric_relabel_configs 是保存数据前的最后一步编辑。默认行为就是一把不想要的样本直接丢掉，不进 TSDB——这是控制"序列数 / 磁盘占用"最有效的手段。

# 4.8　七个实战案例（含课堂上改了四遍的那个）

# 案例 1　把默认标签拼成一个 endpoint

目标：把 __scheme__ / __address__ / __metrics_path__ 拼成 http://10.0.0.101:9100/metrics，存到新标签 endpoint。

  - job_name: 'k8s-node'
    static_configs:
      - targets: ['10.0.0.104:9100','10.0.0.105:9100','10.0.0.106:9100']
    relabel_configs:
      - source_labels:
          - __scheme__
          - __address__
          - __metrics_path__
        regex: "(http|https)(.*)"
        separator: ""                 # ⭐ 空分隔符 → 三段直接连起来
        target_label: "endpoint"
        replacement: "${1}://${2}"
        action: replace

逐步推导（以 10.0.0.101:9100 为例）：

步骤结果
① 取三个 source_labels 的值http / 10.0.0.101:9100 / /metrics
② separator: "" 拼接http10.0.0.101:9100/metrics
③ 用 (http|https)(.*) 匹配分组 1 = http，分组 2 = 10.0.0.101:9100/metrics
④ replacement: "${1}://${2}"http://10.0.0.101:9100/metrics
⑤ 赋给 target_label: endpointendpoint="http://10.0.0.101:9100/metrics"

💡 为什么 separator 要设成空串？
默认是 ;，拼接会得到 http;10.0.0.101:9100;/metrics。用 (http|https)(.*) 去匹配时，分组 2 会变成 ;10.0.0.101:9100;/metrics——多出两个分号，结果就错了。
空分隔符让三段"无缝拼接"，正好凑成合法 URL。

验证：Targets 页展开某个 target，endpoint 标签出现了。

# 案例 2　用 labelmap 生成 job_name / app_name

目标：把所有名为 job 或 app 的标签，复制出一个带 _name 后缀的新标签（值不变）。

先加一个自定义标签：

    static_configs:
      - targets: ['10.0.0.104:9100','10.0.0.105:9100','10.0.0.106:9100']
        labels: {app: 'k8s-node'}
    relabel_configs:
      - regex: "(job|app)"
        action: labelmap
        replacement: "${1}_name"

结果：

原标签新标签
job="k8s-node"job_name="k8s-node"
app="k8s-node"app_name="k8s-node"
（两者都原样保留）—

💡 replacement 默认是 $1。想加后缀就必须显式写 ${1}_name。
这里也更直观地说明了：labelmap 的 regex 匹配的是"标签名"（job、app），而不是它们的值。

# 案例 3　用 labeldrop 删掉旧标签

案例 2 留下了冗余的 job / app。承上再配一条：

    relabel_configs:
      # ……案例 2 的 labelmap ……
      - regex: "(job|app)"
        action: labeldrop

结果：只剩 job_name 和 app_name，job 与 app 被删除。

⚠️ 顺序非常重要：labelmap 必须在 labeldrop 之前。
因为 relabel_configs 是按定义顺序依次执行的——先复制出新的，再删掉旧的。写反了，新的还没生成就先把源删了。

# 案例 4　再改一次名：endpoint → myendpoint

      - source_labels: [endpoint]
        target_label: myendpoint
        action: replace

结果：新增 myendpoint，值为 endpoint 的值。endpoint 仍然保留（replace 不会删源）。

📌 这里体现了课堂上连续做四次标签修改的意义：
relabel_configs 是一个可以叠很多层的"流水线"，每一层只看上一层的输出。
真实配置（比如 kube-prometheus 的 prometheus.yml）里，一个 job 挂 10~20 条 relabel 规则是常态。

# 案例 5　⭐ 用 drop 丢掉 go_* 指标（并解释"为什么旧数据还在"）

目标：node_exporter 暴露了大量 go_* 指标（GC、goroutine、堆），对业务监控没用，删掉能省不少序列。

  - job_name: "node_exporter"
    static_configs:
      - targets:
          - "prometheus.example.com:9100"
          - "10.0.0.201:9100"
          - "10.0.0.202:9100"
    metric_relabel_configs:          # ⭐ 注意：这里必须是 metric_
      - source_labels: [__name__]
        regex: 'go.*'
        action: drop

逐步推导：

  1. source_labels: [__name__] —— 取"指标名"；
  2. regex: 'go.*' —— 匹配以 go 开头的指标名；
  3. action: drop —— 匹配到就丢弃该样本。

结果：go_info、go_gc_duration_seconds 等查不到了。

# ⭐⭐ 但会出现一个"看起来很怪"的现象

改了配置、reload 之后，你去画 go_info 的图，会发现：

图不是空的，而是"画到某个时间点就断了"。

为什么？

时间发生了什么
reload 之前go_* 样本已经被写进 TSDB 了
reload 之后新抓的 go_* 样本在入库前被 drop 掉，不再写入
查询时历史数据仍在硬盘里 → 图上前半段有，后半段断

🧠 这条现象是理解 metric_relabel_configs 本质的最好素材：
它不是"删数据"，而是"不再收数据"。
已经入库的样本不会被回溯删除（要删得靠 promtool tsdb 或等保留期过期）。

⚠️ 另一个非常重要的细节：drop 只对当前 job 生效。
上例中，drop 写在 node_exporter 这个 job 里，所以只有这四台机器的 go_* 被丢；
Prometheus 自己（prometheus job）的 go_* 依然存在。所以你会看到"查询 go_info 还有结果，但机器数变少了"。

# 案例 6　服务发现场景：把 Consul 元数据变成可读标签

  - job_name: 'consul'
    honor_labels: true                  # 保留原有标签，避免被覆盖
    consul_sd_configs:
      - server: 'consul-node1.example.com:8500'
        services: []
      - server: 'consul-node2.example.com:8500'
      - server: 'consul-node3.example.com:8500'
    relabel_configs:
      - source_labels: ['__meta_consul_service']
        target_label: 'consul_service'
      - source_labels: ['__meta_consul_dc']
        target_label: 'datacenter'
      - source_labels: ['__meta_consul_tags']
        target_label: 'app'
      - source_labels: ['__meta_consul_service']
        regex: "consul"
        action: drop                     # 丢掉 consul 服务本身（它不提供业务指标）

这里出现了 __meta_consul_* —— 这就是"服务发现返回的元数据标签"。

💡 通用规律：__meta_<发现机制>_<字段>。

  • Consul：__meta_consul_service、__meta_consul_dc、__meta_consul_tags
  • Kubernetes：__meta_kubernetes_pod_name、__meta_kubernetes_namespace、__meta_kubernetes_service_label_<x>

⚠️ 注意 honor_labels: true：当服务发现/推送方自带的标签与 Prometheus 配置冲突时，保留原标签，避免被覆盖。做服务发现时几乎必加。

# 案例 7　Kubernetes 官方 relabel（看懂它，才算真懂标签管理）

来源：https://github.com/prometheus/prometheus/blob/main/documentation/examples/prometheus-kubernetes.yml

- job_name: 'kubernetes-service-endpoints'
  kubernetes_sd_configs:
    - role: endpoints
  relabel_configs:
    # ① 只抓"打了 prometheus.io/scrape: true 注解"的 Service —— 用 keep 白名单
    - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scrape]
      action: keep
      regex: true

    # ② 注解指定了 https，就把 __scheme__ 改掉
    - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scheme]
      action: replace
      target_label: __scheme__
      regex: (https?)

    # ③ 注解指定了非 /metrics 的路径，改 __metrics_path__
    - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_path]
      action: replace
      target_label: __metrics_path__
      regex: (.+)

    # ④ 把注解里的端口拼进 __address__
    - source_labels: [__address__, __meta_kubernetes_service_annotation_prometheus_io_port]
      action: replace
      target_label: __address__
      regex: ([^:]+)(?::\d+)?;(\d+)
      replacement: $1:$2

    # ⑤ 把 Kubernetes 的 Label 全部提升为 Prometheus 标签（关键！）
    - action: labelmap
      regex: __meta_kubernetes_service_label_(.+)     # replacement 默认 $1

    # ⑥ 把 namespace 和 service 名变成可读标签
    - source_labels: [__meta_kubernetes_namespace]
      action: replace
      target_label: kubernetes_namespace
    - source_labels: [__meta_kubernetes_service_name]
      action: replace
      target_label: kubernetes_name

🎯 看懂这七条，你就掌握了 kube-prometheus 的核心机制。
它们干的事可以概括为三件：

  1. keep：用注解做开关，只监控"想要被监控"的服务；
  2. replace 改 __scheme__ / __metrics_path__ / __address__：让 Prometheus 知道"去哪、用什么协议、抓哪个路径"；
  3. labelmap：把 K8s 的几百个元数据标签"翻译"成人能看懂的业务标签。

⚠️ 好消息：这份配置不用你自己写。官方（以及 kube-prometheus 项目）已经提供完整版本，你拿过来改改就行。但前提是你得看得懂——否则出了问题完全无从下手。

# 4.9　记录规则：给长表达式起个别名

# 4.9.1　两种规则

Prometheus 的 rules 分两种：

类型关键字作用
记录规则（Recording Rule）record⭐ 给表达式起别名，预计算后存成新指标
告警规则（Alerting Rule）alert表达式返回布尔结果，决定是否告警

本节只讲记录规则。告警规则是第 5 章的主角。

# 4.9.2　为什么需要记录规则

两个理由，一个是"懒"，一个是"快"。

理由一：太长了，每次都要写

# 这条表达式算"每次请求平均处理耗时"
request_processing_seconds_sum{job="my_metric"}
  / request_processing_seconds_count{job="my_metric"}

写两次还能忍，写在 20 个面板里就是灾难。起个别名，以后写 req_avg_time 就够了。

💡 类比 Linux 别名：alias rm='rm -i' 和图个方便是一回事。记录规则就是 PromQL 的 alias。

理由二：预计算，查询更快（更重要）

不用记录规则：
   查询时 → 现场扫原始数据 → 现场做除法 → 返回结果   （慢，每次都算）

用记录规则：
   Prometheus 按间隔 → 提前算好存成新指标 → 查询时直接读（快，只读一次）

📌 这就是记录规则的核心价值：把"查询时计算"变成"采集后计算"。
代价是多占一点存储（新指标也要存），换来查询速度与面板加载速度的提升。
面板很慢、Grafana 超时，第一招就是上记录规则。

# 4.9.3　配置：先告诉 Prometheus 规则文件在哪

rule_files:
  # - "rules/*.yml"          # 相对路径，见下方陷阱说明
  - "../rules/*.yml"         # ⭐ 更常见的写法

# ⚠️ 陷阱：相对路径相对于谁？

rule_files 的相对路径，是相对于"配置文件所在目录"，而不是相对于可执行文件目录，也不是相对于工作目录。

我们的目录结构：

/usr/local/prometheus/
├── bin/       prometheus, promtool
├── conf/      prometheus.yml       ← 配置文件在这里
├── data/
└── rules/     record.yml           ← 规则文件在这里

在 conf/prometheus.yml 里写路径时：

rule_files:
  - "record.yml"        # ❌ 它会在 conf/ 下找 record.yml，找不到
  - "/usr/local/prometheus/rules/record.yml"   # ✅ 绝对路径，一定对
  - "../rules/*.yml"    # ✅ 相对路径：从 conf/ 往上一级 → /usr/local/prometheus/ → rules/

🧠 怎么记：prometheus.yml 在 conf/ 里，规则在 rules/ 里，两者是兄弟目录。
所以要先 .. 回到父目录，再进 rules。跟你在 shell 里 cd ../rules 是一模一样的逻辑。

💡 为什么建议单建 rules/ 目录？ 因为后面告警规则、各种记录规则会有几十个文件。全塞在 conf/ 里，配置文件目录会变得难以维护。

# 4.9.4　规则文件的内容

# /usr/local/prometheus/rules/record.yml
groups:
  - name: my_metric_records          # 分组名
    rules:
      - record: req_avg_time         # ⭐ 别名（将来直接当指标名使用）
        expr: |
          request_processing_seconds_sum{job="my_metric"}
            / request_processing_seconds_count{job="my_metric"}

      - record: req_per_minute
        expr: |
          increase(request_count_total{job="my_metric"}[1m])

三个层级：

层级作用
groups一个文件可以有多个组，组之间独立计算（可并发）
name组名，出现在 /rules 页面和 prometheus_rule_group_* 指标里
rules规则列表，每条含 record + expr（可选 labels）

💡 可以给记录规则加标签：

- record: req_avg_time
  expr: ...
  labels:
    team: order
    env: prod

这样新指标自动带上这些标签，便于后续按团队/环境过滤。

# 4.9.5　检查与生效

# 只检查规则文件
promtool check rules /usr/local/prometheus/rules/record.yml
# SUCCESS: 1 rule files found

# 检查整个配置（也会顺带检查规则文件）
promtool check config /usr/local/prometheus/conf/prometheus.yml

# 热加载
systemctl reload prometheus

验证两处：

  1. Web UI → Status → Rules —— 能看到 my_metric_records 这个组和里面的两条规则，状态 OK；
  2. Graph 页面 —— 直接查 req_avg_time，有数据了。

# 4.9.6　⭐ 记录规则的"命名规范"

看 kube-prometheus 的规则文件，你会发现名字都长这样：

method_code:http_errors:rate5m
method:http_requests:rate5m
instance:node_cpu:rate5m

这是官方推荐的三段式命名：

level⏟聚合维度:metric⏟原指标:operation⏟操作\underbrace{\text{level}}_{\text{聚合维度}} : \underbrace{\text{metric}}_{\text{原指标}} : \underbrace{\text{operation}}_{\text{操作}}聚合维度level​​:原指标metric​​:操作operation​​

段含义例
level聚合到的维度instance、method、job
metric来源指标名node_cpu、http_errors
operation做了什么运算 + 时间窗口rate5m、sum、avg

🧠 为什么用冒号？ 因为第 1 章讲过——冒号是专门留给记录规则的，普通 Exporter 不能用。这样一眼就能看出"这是预计算指标，不是原始指标"。

# 4.10　告警概览：为下一章铺路

# 4.10.1　告警规则 vs 记录规则

记录规则告警规则
关键字recordalert
表达式返回数值（求和、比率、耗时…）布尔结果（真/假）
输出一条新时间序列一条告警（pending / firing）
类比Linux 别名Zabbix 的触发器表达式

💡 和 Zabbix 的对应关系：
Zabbix 里写"CPU 利用率 > 80%"这种触发器表达式，在 Prometheus 里就叫告警规则。逻辑完全一样：表达式成立 → 触发；不成立 → 不触发。

# 告警规则的样子（第 5 章详讲）
groups:
  - name: node_alerts
    rules:
      - alert: HighMemoryUsage
        expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100 > 80
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "主机 <!--swig￼7--> 内存使用率超过 80%"

# 4.10.2　⭐ 职责分离：谁判断、谁通知

这是初学者最容易搞混的一点：

flowchart LR
    P["Prometheus Server<br/>① 有指标<br/>② 按规则周期性计算<br/>③ 判断条件是否成立"]
    A["Alertmanager<br/>① 收到告警<br/>② 去重/分组/抑制/静默<br/>③ 按路由发送"]
    U["接收方<br/>邮件 / 钉钉 / 企业微信<br/>短信 / Webhook"]

    P -->|"只发'告警指示'"| A
    A --> U
谁负责什么为什么是它
Prometheus什么时候告警（判断条件）只有它手里有指标数据
Alertmanager告警发给谁、怎么发（通知治理）这才是它擅长的

🧠 一句话：Prometheus 是"发现问题的人"，Alertmanager 是"负责通知的人"。
装完 Prometheus 不等于能告警——还必须部署 Alertmanager。

# 4.10.3　Alertmanager 的五个核心能力

能力解决什么问题
去重（Dedupe）完全相同的告警只保留一条
分组（Grouping）相似告警合并成一条（如 20 台机器同时磁盘满 → 一条告警）
抑制（Inhibition）A 挂了导致 B 也挂，只报 A（A 是根因）。否则你分不清谁是病根
静默（Silence）一段时间内暂停告警（如停服维护、调试期间），避免垃圾告警
路由（Routing）按规则发给不同的人 —— 就是 Zabbix 的"分级告警"

"抑制"为什么重要？ 举个真实例子：机房交换机故障，200 台机器全部 up==0。没有抑制 → 你收到 200 条告警；有抑制 → 只收到"交换机不可达"一条，直接指向根因。

"路由"能实现分级告警：

级别 1：告警 → 值班运维（邮件 + 钉钉）
   ↓ 15 分钟未恢复
级别 2：告警 → 运维主管（电话）
   ↓ 30 分钟未恢复
级别 3：告警 → 技术总监（电话 + 短信）

📌 这五个能力的具体配置（alertmanager.yml、route、inhibit_rules、silences）是第 5 章的内容。现在只需要建立"Prometheus 判断 + Alertmanager 通知"这个基本认知。

# 4.12　面试高频问答

Q1：业务指标怎么采集？

三条路：① 如果应用能改代码，用官方客户端库（prometheus_client / client_golang / client_java）做 Instrumentation，暴露 /metrics；② 如果不能改代码，看是否有社区 Exporter；③ 如果是短周期任务，用 Pushgateway。
自己写 Exporter 的核心就是"起一个 HTTP 服务，在 /metrics 上按 Prometheus 文本格式输出数据"，各语言库已经封装好，几十行代码即可。

Q2：relabel_configs 和 metric_relabel_configs 有什么区别？

两个区别：执行时机和操作对象。
relabel_configs 在抓取之前执行，操作的是 target，此时能用到 __address__、__scheme__、__metrics_path__、__meta_* 这类私有标签，用来附加元数据、过滤目标、改标签名。
metric_relabel_configs 在抓取之后、入库之前执行，操作的是每一条样本，能用 __name__ 和指标自带标签，用来删指标、删敏感标签、改指标名。

Q3：想删掉 go_* 指标，怎么配？为什么删完之后图上还有一部分数据？

在对应的 job 里加：

metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'go.*'
    action: drop

图上还有数据，是因为这个配置只阻止新数据写入，不会删除已经落盘的样本。所以历史区间有数据、之后断层。要彻底删除需要等保留期过期或使用 TSDB 管理工具。

Q4：labelmap 和 labeldrop 有什么区别？

两者都对标签名做正则匹配。labelmap 会复制出符合条件的新标签（旧标签保留），常用于批量提升元数据标签；labeldrop 会删除符合条件的标签，常用于清理。
实践中经常成对使用：先 labelmap 生成新名字，再 labeldrop 删掉旧名字。顺序不能反，因为 relabel 是按定义顺序依次执行的。

Q5：什么是记录规则？有什么用？

记录规则（record）就是给一条复杂的 PromQL 表达式起别名，由 Prometheus 按 evaluation_interval 周期性预先计算，结果作为一条新的时间序列存进 TSDB。
好处有两个：① 以后直接写短名字，不用重复长表达式；② 查询时直接读结果，而不是现场计算，大幅提升面板加载速度。
命名推荐三段式 level:metric:operation，并且用冒号——冒号是专门为记录规则保留的。

Q6：Prometheus 装好了就能告警吗？

不能。Prometheus 只负责按规则判断是否该告警（因为它手里有数据），实际的告警发送必须由独立的 Alertmanager 完成。Alertmanager 负责去重、分组、抑制、静默和路由。

# 实验四　完整复现"改四遍标签"（强烈推荐）

按顺序在同一个 job 上叠加，每一步都去 Targets 页确认效果：

    # ① 先加一个自定义标签
    static_configs:
      - targets: ['10.0.0.104:9100','10.0.0.105:9100','10.0.0.106:9100']
        labels: {app: 'k8s-node'}

    relabel_configs:
      # ② 拼出 endpoint
      - source_labels: [__scheme__, __address__, __metrics_path__]
        regex: "(http|https)(.*)"
        separator: ""
        target_label: "endpoint"
        replacement: "${1}://${2}"
        action: replace

      # ③ labelmap 生成 xxx_name
      - regex: "(job|app)"
        action: labelmap
        replacement: "${1}_name"

      # ④ labeldrop 删掉旧名
      - regex: "(job|app)"
        action: labeldrop

      # ⑤ endpoint 再复制一份
      - source_labels: [endpoint]
        target_label: myendpoint
        action: replace

每一步的预期变化：

步骤标签变化
初始instance、job（+ 隐藏的 __*）
①多了 app="k8s-node"
②多了 endpoint="http://10.0.0.104:9100/metrics"
③多了 job_name、app_name（job/app 仍在）
④job、app 消失，只剩 job_name、app_name
⑤多了 myendpoint（endpoint 仍在）
