# 2.1　开工之前：先把拼图摆好

# 2.1.1　五个软件，各管一段

第 1 章我们列过组件职责表，现在把它落成 "要装什么"：

软件默认端口一句话职责类比 Zabbix

📌 一个重要认知：Prometheus Server 只做两件事 —— 采集、存储。它自带的那个 Web 界面（9090）只用于调试查询，从来没打算让你拿它当监控大屏。所以 "要装 Grafana" 不是可选项，而是必选项。

# 2.1.2　部署拓扑：谁装在哪

三条部署原则（经验，不是规定）：

  1. Prometheus / Grafana / Pushgateway 可以装在同一台（实验环境、小规模环境），也可以分开装。分开装的好处是性能互不干扰、故障不连带。
  2. Node Exporter 必须装在被监控的每一台机器上，一台不能少 —— 包括 Prometheus 自己那台，因为监控系统本身也需要被监控。
  3. 生产环境请把 --storage.tsdb.path （数据目录）独立挂一个分区，避免数据把根分区写满导致整机不可用。

# 2.1.3　版本怎么选：先看兼容性

监控栈是 "多组件协同"，版本乱配最容易出问题。下面是一套经过验证、兼容性良好的企业级组合：

⚠️ 关于 2.x 还是 3.x

Prometheus 已经发布了 3.x，并且提供了 LTS（长期支持） 版本。课程的演示环境用的是 3.5.0 LTS，功能上比 2.x 多了些改进。
但要注意：大量企业存量环境仍然是 2.53.x，生态里的部分 Exporter、Dashboard、规则文件是按 2.x 写的。所以：

  • 新环境可以上 3.x LTS；
  • 接手老环境时不要手贱升级主版本；
  • 预发布版（rc /beta/ 带 -rc 后缀）一律不要装到生产，它不是给生产用的。

  • 镜像可以做得很小 —— 甚至可以 FROM scratch 。

它的收益是什么？—— 能通过 API 触发 reload。
但问题是：我们本来就有 systemctl reload prometheus （靠 ExecReload 发 SIGHUP），效果完全一样，还不需要暴露任何危险接口。

我在很多人的 service 文件里见过这一行，他们大多不知道这行意味着 "谁都能远程关掉你的监控"。别做那个人。

📌 分清两类配置：

  • 配置文件（ prometheus.yml ） 里的东西 → 可以热加载；
  • 命令行启动参数（如 --storage.tsdb.path 、 --web.listen-address ）→ 必须重启才能生效。

改了什么，就用对应的方式生效，不要图省事一律 restart。

# 2.4.4　顺带一提：谁来监控 Prometheus 自己

/-/healthy 和 /-/ready 的价值在于：它们让外部系统可以监控 Prometheus 本身。

Prometheus 监控万物  ——  但 Prometheus 挂了，谁来发现？

三种常见做法：

  1. 双机互监控：A 的 Prometheus 抓 B 的指标，B 的抓 A 的，任一方挂了另一方告警；
  2. 外部探活：另一个系统（Zabbix / 云监控 / 负载均衡健康检查）定时 curl /-/healthy ；
  3. up 指标自监控：用另一个 Prometheus 实例抓本实例的 /metrics ，看 up{job="prometheus"} 。

💡 回到第 1 章的比喻：警察管普通人，那谁管警察？—— 这既是技术问题，也是一个非常好的面试发散点。

保留期的取舍（面试常问）：

磁盘占用≈活跃序列数×采样频率×保留时长×单点字节数\text{磁盘占用} \approx \text{活跃序列数} \times \text{采样频率} \times \text{保留时长} \times \text{单点字节数}磁盘占用≈活跃序列数×采样频率×保留时长×单点字节数

举例：10 万条活跃序列、每 15 秒采一次、保留 15 天、压缩后按 1.5 字节 / 点估算：
100000 \times \frac{86400}{15} \times 15 \times 1.5 \approx 1.3\ \text

注意：这个公式只用于量级估算。真实占用还要看标签基数、chunk 对齐、索引大小等。但把 "序列数" 和 "采样频率" 作为两个乘法因子放在分子上，这个直觉是对的 —— 序列爆炸和采集频率过高，是磁盘被打满的两大主因。

# 2.6.3　 scrape_configs 的结构

三个概念对应第 1 章的知识点：

  • 一个 scrape_configs 下可以有多个 job，job 就是分类（同一类指标的机器放一个 job）；
  • 一个 job 下的 static_configs.targets 里每一项，就是一个 instance（实例），格式 ip:port ；
  • labels 是给这个 job 下所有目标附加的标签，可用于后续 PromQL 过滤。

# 2.8　Node Exporter：把主机指标 "出口" 出去

# 2.8.1　为什么必须有它

回到第 1 章的结论：Prometheus 的所有指标都必须以 HTTP 形式暴露。

而 Linux 操作系统本身不提供 HTTP 指标端点。你不可能让内核主动开个端口给你读 /proc/stat 。

所以中间必须有个 "转换器"：

Node Exporter 干的事：

  1. 读取本机的 /proc 、 /sys 、系统调用，拿到 CPU、内存、磁盘、网络、文件系统等原始数据；
  2. 转换成 Prometheus 文本格式（ # HELP / # TYPE / 指标 值 ）；
  3. 在本机 9100 端口起一个 HTTP 服务，把结果暴露在 /metrics 。

🧠 名字的由来：它把本节点的指标 " 出口（export）"出去，让 Prometheus 来" 进货 "。你不" 出口 "，人家就采不到 —— 这个命名非常形象。

和 Zabbix 的对照：

ZabbixPrometheus
采集代理zabbix-agentnode_exporter
通信协议Zabbix 专有协议HTTP/HTTPS
数据方向Server 拉（被动）或 Agent 推（主动）只有 Server 拉
谁的客户端 / 服务端Server 是服务端，Agent 是客户端⭐ 反过来了：Prometheus 是 HTTP 客户端，Node Exporter 是 HTTP 服务端

最后一行请特别注意：角色是反的。Prometheus 主动发起 HTTP 请求（像浏览器），Node Exporter 被动响应（像 Web 服务器）。

# 2.9.4　"抓不到数据" 五步排查法

把上面的经验固化成流程，以后照着走：

步骤动作判断依据结论
① 目标端自测在目标机上 curl -s localhost:9100/metrics \| head有输出？无 → exporter 没起 / 端口不对
② 跨机自测在 Prometheus 机上 curl -s <target>:9100/metrics通了？不通 → 防火墙 / 监听地址是 127.0.0.1 / 网络不通
③ 看 TargetsWeb UI → Status → TargetsUP / DOWN + 错误信息DOWN → 错误信息直接指出原因
④ 看配置Status → Configuration新 job 在不在、targets 对不对不在 → reload 没成功 / 配置语法被拒
⑤ 看日志journalctl -u prometheus -n 50有无 Error reloading config有 → 配置有问题

四个高频根因（按出现频率排序）：

  1. 端口写错（ 9100 → 9010 / 9091 / 910 ）；
  2. 服务监听在 127.0.0.1 而不是 0.0.0.0 —— 本机 curl 通、跨机不通，这是最迷惑人的一种；
  3. 防火墙 / 安全组没放行（ firewalld 、 ufw 、云安全组）；
  4. 改完没 reload /reload 失败但没人看日志。

💡 还有一个 "假故障"：指标有延迟。刚配好就查，必然查不到 —— 必须等至少一个 scrape_interval 。学习时把间隔调成 10s ，能少等很多；但生产不要低于 10s，否则序列数与磁盘写入会成倍增长。

原因一：指标名变了（版本兼容问题）

# 2.10.6　时间显示：UTC 还是本地时间

Prometheus 内部统一使用 UTC 时间戳。Grafana 面板默认可能按 UTC 显示，导致 "我明明下午 4 点起的服务，图上显示 8 点"。

解决：Dashboard 右上角时间选择器 → 切到 Browser Time / Local。

💡 这不是 bug，是时区约定。记住：Prometheus 存 UTC，展示时再转本地时区。 排查告警时间对不上时，先确认时区。

# 2.11　递归之美：监控 Grafana 自己

# 2.11.1　那条 "绕一圈" 的链路

这是本章最反直觉、也最值得理解的一个知识点。

问题：我想在 Grafana 上看到 Grafana 自己的指标，怎么办？

直觉答案：Grafana 自己展示自己就行了嘛。

正确答案：不行。必须绕一圈。

为什么必须这样？

Grafana 是 "展示层"，不是 "数据源"。它只能从数据源读数据，而它自己不是数据源。

即使要展示 Grafana 自己的指标，也必须：

  1. Grafana 把自身指标暴露在 :3000/metrics ；
  2. Prometheus 去采集它（在 prometheus.yml 里加一个 job）；
  3. Grafana 通过 Prometheus 数据源把这些指标查出来画图。

同理可推：Prometheus 自己的指标也是这么来的 ——Prometheus 默认就采集自己（ localhost:9090 ），所以 Prometheus Stats 面板有数据；而 Grafana metrics 面板没数据，因为没人去采集 Grafana。

# 2.12　Pushgateway：给 "抓不到" 的指标开一扇门

# 2.12.1　为什么会有这个组件

考虑一个真实需求：统计当前有多少用户登录在这台机器上。

就一个数字。但问题是：

  • 它是由一条命令临时算出来的，不是某个常驻服务持续提供；
  • 机器上没有 HTTP 服务去暴露这个数字；
  • Prometheus 只会 GET /metrics —— 它没法 "执行一条命令"。

Prometheus 抓不到它。 这就是 Pushgateway 存在的理由。

# 2.12.2　工作原理：一个 "代收点"

它就是一个 "代理 / 中转站"：

你没有 HTTP 服务？我替你有。
你把数据交给我（POST /metrics），我挂在 /metrics 上等 Prometheus 来拉。

关键结论：Pushgateway 并没有改变 Prometheus"只拉不推" 的本质 —— 它只是给 "无法被拉" 的目标，额外增加了一个 "可以被拉" 的中转点。数据链路的最后一跳，仍然是 Pull。

# 2.12.3　与 Exporter、与 Zabbix Proxy 的对照

这是最容易混淆的一组概念，用表格彻底分清：

维度ExporterPushgatewayZabbix Proxy
采集方向被动（等 Prometheus 来拉）主动接收（应用推过来）主动采集后上报
装在哪儿⭐ 每个被监控节点都要装一个⭐ 只装一个（任何位置都行，不必在被监控端）每个区域 / 网段一个
是否需要专属⭐ 每种应用一个专用 Exporter（MySQL、Redis 各有各的）一个就够，所有应用都能往它推一个通用的即可
类比zabbix-agentzabbix-proxyzabbix-proxy

🧠 记忆锚点：

  • Exporter 是 "每个应用配一个专用翻译官"——MySQL 的翻译官不懂 Redis 的话。
  • Pushgateway 是 "一个公共收件箱"—— 谁都能往里投信，它不挑。

# 2.12.4　必须知道的四个固有缺陷

Pushgateway 官方文档明确定义了这些局限，面试常问，生产必知：

缺陷具体表现后果
① 单点瓶颈只有一份 Pushgateway，多个应用同时推送进程挂了 → 全链路数据中断
② up 指标失效Prometheus 只能看到 Pushgateway 是否活着，看不到真实应用是否活着⭐ 服务挂了，旧数据还在，图表上一片 "正常"—— 假存活！
③ 永不清理推上去的数据永久保留并持续暴露，除非手动 DELETE已下线任务的指标一直 "诈尸"
④ 不做校验脚本算错了、推了脏数据，它照单全收错误数据进入 TSDB，无法追溯

🚨 ② 号缺陷最危险。举个真实场景：你的备份任务每天推一次 "备份成功 = 1"。某天任务彻底挂了，不再推送 —— 但 Pushgateway 上那条 backup_success 1 还在，Prometheus 一直抓到 1 ，你的大屏一直显示 "备份正常"。你会在真正需要备份的那天发现它已经坏了三个月。

应对：在应用侧实现 "心跳 / 时间戳" 指标，用 time() - backup_last_success_timestamp > 86400 这类表达式告警。不要指望 up 。

不加它时，Prometheus 会把自己配置里的 job="pushgateway" 和 instance="10.0.0.100:9091" 强加到所有指标上 —— 于是所有应用推上来的指标看起来都来自同一台机器，标签全被覆盖了。

# 2.15　面试高频问答

Q1：Prometheus 有几种安装方式？生产推荐哪种，为什么？

包安装、二进制、Ansible、Docker、Docker Compose、K8s 六种。
生产推荐二进制 + systemd：版本可控（不被发行版仓库锁死）、零依赖（Go 静态编译）、目录布局自由（配置 / 数据可分离、数据目录可独立分区）、排障直观（日志、进程、路径都在明处）。大规模机器建议 Ansible，云原生环境用 Operator / Helm。

Q2： --web.enable-lifecycle 是干什么的？为什么不建议开？

它允许通过 HTTP API 触发 /-/reload 和 /-/quit 。风险在于无任何认证：任何能访问 9090 的人都能 POST /-/quit 直接把监控服务关掉。而 reload 这件事用 systemctl reload （配合 ExecReload=/bin/kill -HUP ）完全能实现。所以生产保持默认 false。

Q3：改了配置文件怎么让它生效？

三步： promtool check config 校验语法 → systemctl reload prometheus （SIGHUP 热加载）→ 在 Status → Configuration 确认生效、Status → Targets 确认目标 UP。
注意：改启动参数（如 --storage.tsdb.path ）必须 restart，热加载不了。

Q4：为什么 Node Exporter 装在容器里要 --net=host --pid=host -v /:/host ？

因为它的职责是采集宿主机的指标，而不是容器自己的。共享网络命名空间才能看到真实网卡；共享 PID 命名空间才能看到宿主机全部进程；挂载宿主机根目录并指定 --path.rootfs=/host 才能读到真实的 /proc 、 /sys 和文件系统使用率。否则采到的全是容器 overlay 里的数据。

Q5：Pushgateway 有什么缺点？

四个：① 单点故障；② up 指标失效（看不到真实目标存活，服务挂了旧数据还在，造成 "假存活"）；③ 数据永不自动清理，必须手动 DELETE；④ 不做数据校验，脏数据照单全收。
因此它只适合短周期 / 一次性任务的指标，长期运行的服务应该用 Exporter。

Q6：如何监控 Grafana 自身？

Grafana 自带 /metrics 端点（:3000），在 prometheus.yml 里加一个 job 采集它，然后在 Grafana 里用 Prometheus 数据源查询展示。注意它不能自己展示自己 ——Grafana 是展示层不是数据源，必须经 Prometheus 中转。

Q7： honor_labels: true 有什么作用？

采集 Pushgateway 时必须加。否则 Prometheus 会用自己配置的 job / instance 覆盖掉推送方设置的标签，导致所有应用的数据都像是同一个来源。加上之后保留 Pushgateway 上的标签，Prometheus 自己的标签改名为 exported_job / exported_instance 。
