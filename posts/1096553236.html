# 3.1　先把地基夯死：时间序列与样本

# 3.1.1　时间序列（Time Series）

Prometheus 采用时间序列存储监控数据。

时间序列：按照时间顺序记录系统、设备或应用状态变化的数据集合。

数据按固定采集周期（如 15s、30s）不断采集，随着时间推移形成一串离散的数据点 —— 这就是时间序列。

放到坐标系里就非常直观：X 轴是时间，Y 轴是数值，把点连起来就是我们看到的监控曲线。Grafana 里那一条条折线，本质就是若干个时间序列。

# 3.1.2　样本（Sample）

每采集一次，就产生一个样本。一个 Sample 由两部分组成：

组成内容
keyMetric 名称 + Label 集合 + Timestamp（毫秒精度）
valuefloat64 格式的数值

📌 记住这个 "没有例外" 的事实：Prometheus 的样本值只能是 float64。
没有字符串、没有布尔、没有整型。你看到的 1 、 0 、 200 ，全是浮点数的字面表现。

# 3.1.3　唯一标识与五条铁律

时间序列的唯一标识 = Metric Name + Label Set。

围绕这句话，有五条推论必须记牢：

#铁律后果
1指标名 + 标签的特定组合代表一条时间序列查询时永远在 "选序列"
2不同指标名代表不同时间序列名字就是身份
3指标名相同、标签不同，是不同时间序列method="GET" 与 method="POST" 是两条
4更改任何标签值（含增删标签）都会创建新序列标签一改，历史数据就 "接不上"
5应尽量保持标签稳定标签乱变 → 序列爆炸 → 图形 / 告警 / 记录规则全部失效

⚠️ 第 4、5 条是生产事故级别的认知。第 4 章讲标签管理时，你会亲眼看到 "改了一个标签，图上出现断层" 的现象 —— 那正是这条铁律在起作用。

# 3.2　四种表达式类型：PromQL 的 "类型系统"

# 3.2.1　什么是 PromQL

官方文档：https://prometheus.io/docs/prometheus/latest/querying/basics/

PromQL（Prometheus Query Language）是 Prometheus 内置的函数式表达式语言，用于实时查找和聚合时间序列数据。

它的结果有三个去处：

  1. 图表展示（Grafana / 内置 Graph）；
  2. 表格展示（表达式浏览器）；
  3. HTTP API 提供给外部系统（告警、自动化平台、自研大屏）。

📌 默认时间基准：不指定时间时，以 "当前时间" 为基准点取数。

# 3.2.2　四种结果类型

任何一个 PromQL 表达式（或子表达式），计算结果必为以下四种之一：

类型中文定义直观理解
instant vector即时向量一组时间序列，每条序列各含一个样本，共享同一时间戳一个时间点上的一组数
range vector范围向量一组时间序列，每条序列含一串随时间变化的样本一个时间段内的一组数
scalar标量一个简单的浮点数值一个 "裸数字"，如 1024
string字符串一个简单字符串目前基本用不到
instant vector  →  node_load1
                   ↑ 4 台机器 = 4 条序列，每条 1 个值

range vector    →  node_load1[5m]
                   ↑ 4 台机器 = 4 条序列，每条 20 个值（15s×20=5m）

scalar          →  1024
string          →  "hello"

# ⭐ 为什么统计结果 "不那么整"？

这是一个非常好的理解 Prometheus 设计的机会。

不同时间序列的抓取时间点，并不严格对齐。

原因：如果所有 target 都在同一毫秒被抓取，几百上千个 target 会在那一瞬间把 Prometheus 压出尖峰。所以 Prometheus 会刻意为每个 target 稍微错峰（差几毫秒到几百毫秒）。

后果：趋势上准确，绝对数值上并不精确。 比如 [1m] 在 10s 间隔下，采样点数可能是 6 个，也可能是 5 个或 7 个。

💡 这解释了大量 " 为什么 increase() 算出来是 5.8 而不是 6 " 的困惑。不是 bug，是设计。

# 3.3.4　偏移修饰符 offset

所有选择器默认以 "当前时间" 为基准。 offset 就是把这根基准线往回推。

三条要点：

  1. offset 必须紧跟在选择器后面，中间不能断开；
  2. offset 偏移的是时间基点，不是区间长度；
  3. 既有范围又有偏移时：先定基点，再取范围。 [5m] offset 3m = "3 分钟前那一刻，往前数 5 分钟"。

💡 典型用途：环比

# ⭐ 核心认知：Counter 的总数几乎没有意义

node_cpu_seconds_total{cpu="0",mode="idle"} = 28375.49 —— 这个数字本身说明不了任何问题。它只是 "从开机到现在，CPU 0 空闲了多少秒"。

有价值的是它的 "变化速度"。

所以 Counter 几乎从不直接使用，而是配函数降维：

函数得到什么用途
rate()每秒平均增长率⭐ 算 QPS、CPU 使用率
irate()最近两点的瞬时增长率看突发尖峰
increase()区间内增长总量算 "这段时间一共处理了多少"
topk()排名前 K 的序列找最忙的接口

⚠️ Counter 重置的处理：进程重启后 Counter 归零，直接相减会得到负数。
rate() / irate() / increase() 已经内置处理了重置（自动检测下降并补偿），所以永远用函数算，不要自己写 current - offset 。

# 3.4.4　Histogram（直方图）

用于统计数据分布。服务端（Prometheus）负责计算分位数。

核心机制：累积桶（Cumulative Bucket）

把取值范围切成若干连续、相邻但不重叠的区间（bucket），统计每个区间里有多少个观测值。累积的意思是： le="0.1" 的桶里，包含了所有 ≤0.1 的样本，也自然被计入 le="0.5" 的桶。

一个 Histogram 指标会展开成多条时间序列：

序列含义
<basename>_bucket{le="<上界>"}落入该桶（含更小桶）的样本数
<basename>_bucket{le="+Inf"}全部样本数（最后一个桶）
<basename>_sum所有观测值的总和
<basename>_count观测总次数（本质是 Counter）

范例：

读法：

  • 有 6028 次压缩，全部落在 6.55e+06 秒以内（因为从 le=6.5536e+06 开始就跳到 6028 了）；
  • 平均耗时 = _sum / _count = 10734846288 / 6028 ≈ 178 万秒。

计算分位数：

Histogram 的三个优势：

  • 桶设计一次，服务端随意算（P50 / P90 / P99 都能事后算）；
  • 支持聚合（多实例的桶可以相加后再算分位）；
  • 单独提供 _sum 和 _count ，从而可以算平均值。

# 3.4.6　Histogram vs Summary：一表定生死

维度HistogramSummary
分位数在哪算Prometheus 服务端（ histogram_quantile ）客户端（每次采样时算好）
能否事后换分位数✅ 任意（P50/P90/P99 随时算）❌ 只能用客户端预定义的
能否多实例聚合✅ 桶可相加后再算❌ 分位数不可聚合
客户端开销小（只是计数）大（要维护滑动窗口与分位计算）
服务端开销大（分位计算消耗资源）小（直接读数）
准确性受桶划分影响，是估算值客户端流式计算，相对精确
典型用途⭐ 绝大多数场景首选（请求耗时、响应大小）分位数固定、实例少、不能聚合的场景

🧠 选型口诀：能用 Histogram 就用 Histogram。

因为 "分位数不能聚合" 是致命缺陷：你有 10 个实例，每个实例的 P99 是 100ms，整体 P99 绝不是 100ms—— 它可能差得很远。只有 Histogram 的桶相加后才能算整体的分位数。

唯一例外：客户端只需暴露一个固定的高分位数（如 SLO 的 P99.9），且不需要聚合。

⚠️ 严谨补充：笔记里说 Summary "不支持 sum 或 avg 一类的聚合运算"—— 这句话只对分位数成立。 <basename>_sum 和 <basename>_count 是可以正常聚合的（它们本质是 Counter）。所以 Summary 可以算平均值，不能算分位数。

# ⭐ 关键区别：加不加 bool

这是 PromQL 与 "普通编程语言" 最大的不同点，必须理解透。

写法语义结果
expr > 80过滤（filter）只保留 "比较成立" 的序列，不成立的直接消失
expr > bool 80转换（bool）保留所有序列，成立的输出 1 ，不成立的输出 0

📌 官方说明：使用 bool 后，布尔运算不会过滤时间序列，而是依次把每个样本与标量比较，结果 0 或 1 形成一条新时间序列。

🎯 告警规则里大量使用 +bool 会比较 "好用"，但要注意：告警规则本身用 expr > 80 就够了（Alertmanager 只需要 "有没有结果"）。 bool 更适合画 "状态图" 和做 "计数"（如 count(up == bool 0) 数挂了几台）。

# 3.8.2　⭐ 核心四兄弟： increase / rate / irate / delta

这是全章最需要 "真的理解" 的部分。

先看它们各自的定义：

函数输入输出一句话
increase(v[d])range vector区间内增长总量"这段时间一共涨了多少"
rate(v[d])range vector每秒平均增长率"平均下来每秒涨多少"
irate(v[d])range vector最近两点的瞬时增长率"现在这一刻每秒涨多少"
delta(v[d])range vector区间首尾差值（可负）给 Gauge 用，不是给 Counter 用
idelta(v[d])range vector最近两点差值给 Gauge 用

⚠️ 先纠正一个常见误解： increase() 不是 "最后两个点相减"。
它等于 rate(v[d]) × 区间秒数 ，也就是基于区间首尾值做外推估算得到的增长总量。
（笔记里写 "increase = last 值 − last 前一个值"，那是 idelta 的语义，不是 increase 。）

# 用 "薪水" 理解 increase 和 rate （讲师原话，非常好用）

假设你的月薪从 1 万 涨到了 2 万：

  • increase = 1 万（一共涨了 1 万）
  • 但这个数字意义有限 —— 因为你还得知道 "用了多久"：
    • 一年涨 1 万 → 变化率 = 1 万 / 年
    • 十年涨 1 万 → 变化率 = 1000 / 年

结论：光看 "涨了多少" 意义不大，"单位时间涨了多少" 才有意义。这就是 rate 。

rate=区间末值−区间首值区间秒数\text{rate} = \frac{\text{区间末值} - \text{区间首值}}{\text{区间秒数}}rate=区间秒数区间末值−区间首值​

# rate 的计算方式与 "被平均" 问题

假设采集间隔 10s，取 [1m] ，区间内有 6 个采样点：

t=0s    t=10s   t=20s   t=30s   t=40s   t=50s   t=60s
 100     110     120     130     140     150     160
  ↑                                              ↑
首值                                           末值

rate   = (160 - 100) / 60 = 1.0   ← 只用首尾两个点，中间 4 个点被"忽略"

问题：如果中间发生了剧烈波动（比如 t=50s 时突然涨到 500 又回落）， rate 完全看不出来 —— 因为它已经把这段变化 "平均" 掉了。

# irate 的计算方式：只看最后两步

irate = (末值 - 末值前一个点) / 这两点的时间差
      = (160 - 150) / 10 = 1.0    ← 只看最后两个点

优势：能反映最近一瞬间的变化，尖峰不会被抹平。

场景：前 50 秒请求量平稳（0~10），最后 10 秒暴增到 100+

   数值  │      ╱         │        │              ╱ │

📌 官方建议：

  • irate 适合快速变化的计数器（如高 QPS 的接口）；
  • rate 适合缓慢变化的计数器（如磁盘 IO、网卡流量）。
  • 对快速变化的计数器用 rate ，会削平峰值；除非把区间设得很小来减弱这种效应。

# 实战写法

第 ④ 条拆解：

  1. node_cpu_seconds_total{mode="idle"}[5m] —— 所有 CPU 所有核的空闲时间（range vector）
  2. irate(...) —— 每个核的空闲速率（instant vector）
  3. avg by (instance)(...) —— 把 "多核" 平均掉，得到 "这台机器的平均空闲率"（0~1）
  4. 1 - ... —— 得到使用率（0~1）
  5. * 100 —— 转成百分比

💡 为什么用 avg by (instance) 而不是 sum ？
因为每个核的 idle 速率已经是 0~1 的比例，平均才对； sum 会得到 "核心数" 倍的值，完全错。
这是 PromQL 里最容易算错的指标，面试高频。

# 3.10　面试高频问答

Q1： rate 和 irate 有什么区别？分别什么时候用？

rate 用区间首尾两个值相减再除以区间秒数，得到平均增长率，会把中间的波动抹平； irate 用最后两个采样点相减除以它们的时间差，得到瞬时增长率，能反映尖峰。
快速变化的计数器（高 QPS 接口、突发流量）用 irate ；缓慢变化的计数器（磁盘 IO、网络流量、SLO 统计）用 rate 。

Q2：为什么不能直接画 node_cpu_seconds_total ？

因为它是 Counter，值是 "开机至今的累计秒数"，单调递增，画出来就是一条斜线，毫无意义。必须用 rate / irate 转成 "每秒的增长率" 才有观察价值。

Q3： by 和 without 有什么区别？

by(labels) 是白名单：只按这些标签分组，结果只保留这些标签，等价于 SQL 的 GROUP BY 。
without(labels) 是黑名单：排除这些标签，用其余全部标签分组，结果保留除它们外的所有标签。

Q4：Histogram 和 Summary 怎么选？

优先 Histogram。因为 Histogram 的分位数由服务端用 histogram_quantile 计算，桶可以跨实例相加，所以能算全局分位数，也能事后换分位数；Summary 的分位数在客户端算好，不可聚合（10 个实例的 P99 不能相加得到整体 P99），只能用预定义的分位点。
Summary 只适合分位数固定、实例少、不需要聚合的场景。代价是 Histogram 受桶划分影响，结果是估算值。

Q5： absent() 有什么用？

检测 "指标完全消失" 的情况。有数据返回空，无数据返回 1。因为普通表达式在指标消失时返回空结果，告警不会触发，而 "Exporter 挂了" 恰恰是最需要告警的场景。

Q6： > 80 和 > bool 80 有什么区别？

> 80 是过滤：只保留满足条件的序列，不满足的直接从结果中消失。
> bool 80 是转换：保留所有序列，满足的返回 1，不满足的返回 0，从而形成一条新的 0/1 时间序列。适合画状态图和做计数。

Q7：算占比时经常没结果，怎么排查？

九成是分子分母聚合粒度不一致：一边带多个标签、一边被 sum() 清空，导致两边标签集对不上、无法匹配。解决方法是两边都用相同维度聚合（如都 sum() ），或者用 ignoring(...) / group_left 明确匹配规则。
