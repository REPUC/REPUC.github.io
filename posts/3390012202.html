# 第 5 章　告警（上）：Alertmanager 与告警规则

本章导读

到这里，你的监控系统已经能采、能存、能查、能画了。但它还是"哑"的——出了问题，它不会主动告诉你。

第 4 章我们埋了个伏笔：Prometheus 判断，Alertmanager 通知。本章就把这两端接通。

这一章的核心是三个"三"：

  • 三个组件：Prometheus（判断）+ 告警规则（条件）+ Alertmanager（通知）；
  • 三个状态：Inactive → Pending → Firing；
  • 三个时间：group_wait / group_interval / repeat_interval。

把这三个"三"吃透，告警这块就通了。

学习目标

序号学完本章，你应当能够
1画出告警的完整链路，说清 Prometheus 与 Alertmanager 各自负责什么
2独立完成 Alertmanager 二进制部署，并解释为什么必须显式指定绝对路径
3读懂 alertmanager.yml 的五大模块，用 amtool check-config 校验
4写出完整的告警规则（alert / expr / for / labels / annotations）
5解释 for 为什么必须有，以及 Pending 和 Firing 的区别
6完成邮件告警全流程，并说明三个时间参数的作用
7用 Web 和 amtool 两种方式做告警静默

# 5.1　先把分工讲清楚：为什么必须有两个组件

# 5.1.1　"能看见"不等于"会告警"

监控数据可视化之后，你确实能一眼看出服务是不是正常。但现实是：

没有人能 24 小时盯着大屏。

所以监控系统必须能主动巡检 + 自动通知。这才是监控平台真正的价值所在——甚至可以说：

一个没有告警能力的监控平台，算不上一个平台，顶多是个仪表盘。

# 5.1.2　两段式架构

Prometheus 把告警拆成两个独立组件，各干一件事：

flowchart LR
    subgraph A["① 判断层（Prometheus）"]
        R["告警规则 Alert Rules<br/>expr 周期性计算<br/>返回布尔结果"]
    end
    subgraph B["② 通知层（Alertmanager）"]
        AM["去重 · 分组<br/>抑制 · 静默 · 路由"]
    end
    C["接收方<br/>邮件 / 企业微信<br/>钉钉 / Webhook / Slack"]

    R -->|"只发'告警指示'<br/>(谁、什么级别、什么值)"| AM
    AM --> C
组件负责为什么必须是它
Prometheus + 告警规则什么时候该告警只有它手里有指标数据
Alertmanager告警发给谁、怎么发、发几次消息治理（去重/分组/抑制/静默/路由）才是它的专长

🧠 一句话：Prometheus 是"发现问题的人"，Alertmanager 是"负责通知的人"。

所以：装完 Prometheus ≠ 能告警。 必须再部署一个 Alertmanager，并且在 prometheus.yml 里告诉 Prometheus "Alertmanager 在哪"。

# 5.1.3　Alertmanager 的五个核心能力（本章与下章的主线）

能力解决什么出现在
去重（Dedupe）完全相同的告警只保留一条自动生效
分组（Grouping）相似告警合并成一条通知group_by
路由（Route）按标签把告警发给不同的人第 6 章
抑制（Inhibition）根因告警压制连带告警第 6 章
静默（Silence）一段时间内暂停告警（维护）本章 5.7

💡 为什么"分组"这么重要？ 想象一次机房断电：200 台机器同时 up==0。

  • 没有分组 → 200 条告警，200 封邮件，你的手机被打爆；
  • 有分组 → 1 条"200 个实例不可用"的通知。

这就是 group_by 存在的意义。

# 5.2　部署 Alertmanager

# 5.2.1　二进制安装

下载：https://github.com/prometheus/alertmanager/releases

cd /usr/local
wget https://github.com/prometheus/alertmanager/releases/download/v0.27.0/alertmanager-0.27.0.linux-amd64.tar.gz
tar xf alertmanager-0.27.0.linux-amd64.tar.gz -C /usr/local/
ln -s /usr/local/alertmanager-0.27.0.linux-amd64 /usr/local/alertmanager

两个二进制，各有分工（这点和 Prometheus 一模一样）：

程序作用
alertmanager主程序（告警处理与通知）
amtool客户端工具（配置语法检查 / 静默管理 / 查询告警），相当于 Prometheus 的 promtool

整理目录：

cd /usr/local/alertmanager
mkdir -p bin conf data

mv alertmanager amtool bin/
cp alertmanager.yml conf/

useradd -r -s /sbin/nologin prometheus        # 若已存在会报错，忽略即可
chown -R prometheus:prometheus /usr/local/alertmanager/

💡 说明：data 目录不用手动建也行（程序会自动创建），但父目录必须可写。下一节会看到一个因为"父目录不可写 + 相对路径"而起的真实故障。

# 5.2.2　写 systemd 服务单元

[Unit]
Description=Alertmanager
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/alertmanager/bin/alertmanager \
          --config.file=/usr/local/alertmanager/conf/alertmanager.yml \
          --storage.path=/usr/local/alertmanager/data \
          --web.listen-address=0.0.0.0:9093
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
User=prometheus
Group=prometheus

[Install]
WantedBy=multi-user.target

三个参数的意义：

参数默认值说明
--config.filealertmanager.yml（相对当前目录）配置文件路径，必须显式指定
--storage.pathdata/（相对路径）静默记录、通知日志的落盘位置，⭐ 强烈建议写绝对路径
--web.listen-address:9093⭐ 建议显式写 0.0.0.0:9093，某些环境下 :9093 会绑定异常导致启动失败
systemctl daemon-reload
systemctl enable --now alertmanager.service
systemctl status alertmanager.service

# 5.2.3　两个端口：9093 与 9094

ss -ntlp | grep alertmanager
# LISTEN 0 4096 *:9093 users:(("alertmanager",pid=145545,fd=8))     ← Web/API
# LISTEN 0 4096 *:9094 users:(("alertmanager",pid=145545,fd=3))     ← 集群 gossip

netstat -tnulp | egrep 'Pro|ale'
# tcp  0 0 10.0.0.101:9093 0.0.0.0:* LISTEN 25490/alertmanager
# tcp6 0 0 :::9093         :::*      LISTEN 25490/alertmanager
# udp6 0 0 :::9094         :::*      25490/alertmanager
端口用途
9093Web UI、API、Prometheus 推送告警、/metrics
9094集群内 gossip 通信（TCP + UDP），多实例高可用用（第 6 章）

⚠️ 看到 9094 不要慌，它不是"多开了一个服务"，而是 Alertmanager 的集群成员发现通道。单机部署时它也存在，只是没人来连。

# 5.2.4　⭐ 故障现场一：cannot create directory —— 相对路径 + 权限的双重坑

按最省事的写法启动（不写 --storage.path）：

systemctl start alertmanager
systemctl status alertmanager
# failed

排查过程：

  1. ss -ntlp | grep 9093 —— 端口没起来；
  2. journalctl -u alertmanager -n 50 --no-pager —— 看到关键错误：
level=error msg="failed to initialize notification log" err="mkdir data: no such file or directory"
  1. 理解错误：--storage.path 默认是 data/（相对路径）。相对谁？相对于进程的工作目录。而 systemd 单元里没有设置 WorkingDirectory，进程的工作目录是 /（根目录）。
  2. 于是它尝试 mkdir /data —— 普通用户 prometheus没有根目录的写权限，失败。

第一个修法：把绝对路径写上。

ExecStart=/usr/local/alertmanager/bin/alertmanager \
          --config.file=/usr/local/alertmanager/conf/alertmanager.yml \
          --storage.path=/usr/local/alertmanager/data

但还有第二个坑：如果 /usr/local/alertmanager 的属主不是 prometheus，mkdir data 依然会失败。

chown -R prometheus:prometheus /usr/local/alertmanager/
systemctl restart alertmanager

结论（这是第二遍遇到同类问题了）：

⭐ 凡是"指定数据/日志/配置路径"的参数，一律写绝对路径。
相对路径在交互式 shell 里能跑，在 systemd 里几乎必错——因为两者的工作目录完全不同。
第 2 章 Prometheus 的 data/ 权限问题，根子上也是同一件事。

# 5.2.5　验证与"自己也要被监控"

curl -s http://127.0.0.1:9093/-/healthy
curl -s http://127.0.0.1:9093/metrics | head -20

浏览器访问 http://<ip>:9093/ 可以看到 Alertmanager 的 Web 界面。

然后做一件容易漏掉的事——把 Alertmanager 自己也纳入监控：

scrape_configs:
  - job_name: "alertmanager"
    static_configs:
      - targets: ["10.0.0.100:9093"]

🧠 为什么？ 因为 Alertmanager 也是个长期运行的程序，它挂了你就彻底收不到告警了。
"监控系统的组件本身，也必须被监控"——这是第 4 章反复强调的原则。别因为它"是告警的"就忘了它"也是个程序"。

# 5.3　alertmanager.yml：五大模块

官方文档：https://prometheus.io/docs/alerting/latest/configuration/

# 5.3.1　全景

global:            # ① 全局配置（发件人、超时等）
templates:         # ② 通知模板文件路径
route:             # ③ 路由（告警发给谁）—— 核心
receivers:         # ④ 接收者定义（邮箱、微信、Webhook）
inhibit_rules:     # ⑤ 抑制规则
模块作用本章是否用到
global全局默认值⭐ 用到（SMTP）
templates加载 .tmpl 模板文件第 6 章
route路由树，决定"发给哪个 receiver"⭐ 用到
receivers定义接收者（email_configs / wechat_configs / webhook_configs）⭐ 用到
inhibit_rules抑制规则第 6 章

一个完整的最小配置：

global:
  resolve_timeout: 1m
  smtp_smarthost: 'localhost:25'
  smtp_from: 'ops@example.com'
  smtp_require_tls: false

templates:
  - '/usr/local/alertmanager/tmpl/*.tmpl'

route:
  receiver: 'wang'
  group_by: ['alertname']
  group_wait: 20s
  group_interval: 10m
  repeat_interval: 3h

receivers:
  - name: 'admin'
    email_configs:
      - to: 'admin@example.com'

⚠️ 系统自带的 alertmanager.yml 基本没用。它默认写的是 receiver: 'default' 加一个 webhook_configs: url: 'http://localhost:5001/'——你机器上根本没有 5001 这个服务。
所以：不要试图去"改"默认配置，直接清空重写。 保留结构、内容自己填。

# 5.3.2　global：全局配置

参数作用
resolve_timeout多久没收到该告警的更新，就判定为已恢复（resolved），默认 5m
smtp_smarthostSMTP 服务器地址:端口，如 smtp.163.com:25
smtp_from发件人地址
smtp_auth_username / smtp_auth_password认证用户名 / 授权码（不是登录密码！）
smtp_helloEHLO 域名，如 163.com / qq.com
smtp_require_tls是否强制 TLS。用 25 端口一般设 false；用 465 端口需要另外配 TLS

⚠️ resolve_timeout 有个坑：如果它比 Prometheus 的 evaluation_interval 小太多，可能出现"告警还在，但已经被标记为恢复"的假象。一般设 5m 左右比较稳妥。

# 5.3.3　route：核心中的核心

route:
  receiver: 'email'                    # 默认接收者（兜底）
  group_by: ['alertname', 'cluster']   # 按什么分组
  group_wait: 10s                      # 首次通知等待
  group_interval: 10s                  # 组内更新间隔
  repeat_interval: 10s                 # 重复通知间隔（测试用，生产别这么小）

三个时间参数，是初学者最容易混的一组，必须分清：

参数含义类比
group_wait收到一个告警组的第一条告警后，等多久看看同组还有没有别的告警要一起来等电梯：关门后等 3 秒看看还有没有人冲过来
group_interval同一组告警，多久再发一次更新（组内有新告警加入时）班车发车间隔
repeat_interval同一组告警一直没恢复，多久重复提醒一次闹钟"稍后提醒"

🧠 最有效的记法：

  • group_wait → "攒一攒"（等同伴）
  • group_interval → "合起来"（组内新成员加入时再报）
  • repeat_interval → "再催一遍"（一直没好，定期提醒）

⚠️ repeat_interval 千万别设太小。 设成 10s，一个没恢复的告警每 10 秒发一封邮件——很快就会被 SMTP 服务器判为垃圾邮件而拒收，到那时你连正常的告警都收不到了。

# 5.3.4　receivers：接收者

receivers:
  - name: 'email'
    email_configs:
      - to: 'root@example.com'
        send_resolved: true        # ⭐ 恢复时也发通知

三种常用类型：

配置块用于
email_configs邮件
wechat_configs企业微信（第 6 章）
webhook_configs通用 webhook（钉钉、飞书、自研平台都走这个，第 6 章）

💡 强烈建议所有 receiver 都加 send_resolved: true。
否则你会收到"磁盘满了"的告警，却永远收不到"磁盘恢复了"的通知——一晚上都以为还没修好。

amtool check-config /usr/local/alertmanager/conf/alertmanager.yml

# Checking '/usr/local/alertmanager/conf/alertmanager.yml'  SUCCESS
# Found:
#  - global config

# 5.4　告诉 Prometheus：Alertmanager 在哪

这一步极其容易被忘，而且忘了之后现象非常迷惑：规则页能看到规则，状态也 Firing 了，但一封邮件都收不到。

# 5.4.1　静态配置

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["10.0.0.100:9093"]

# 5.4.2　文件发现（可选，便于批量管理）

alerting:
  alertmanagers:
    - file_sd_configs:
        - files: ["targets/alertmanager*.yaml"]
# /usr/local/prometheus/conf/targets/alertmanager.yaml
- targets:
    - alert.example.com:9093
  labels:
    app: alertmanager

# 5.4.3　生效与验证

promtool check config /usr/local/prometheus/conf/prometheus.yml
systemctl reload prometheus

两个验证点：

  1. Status → Runtime & Build Information 页面，能看到 Alertmanagers 的地址；
  2. Prometheus 指标 prometheus_notifications_alertmanagers_discovered 应大于 0。

# 5.4.4　⭐ 故障现场二：规则 Firing 了，但一条邮件都没有

现象：告警规则写好了、Alertmanager 也部署好了、状态也 Firing 了，就是收不到通知。

排查顺序（请记住这个顺序）：

步骤检查什么判断
①Prometheus → Status → Rules规则在不在？状态是不是 Firing？
②Prometheus → Status → Alerts告警有没有进入 firing？
③prometheus.yml 的 alerting 段配了吗？地址对不对？端口是 9093 吗？
④Alertmanager UI → Alerts 页面告警有没有到 Alertmanager？
⑤Alertmanager UI 里的告警状态firing 还是 suppressed（被抑制/静默了）？
⑥journalctl -u alertmanager有没有发送失败日志？

这次的真实原因：改了 prometheus.yml、也做了语法检查，但忘了 reload。

⭐ 一条铁律：
改配置 → promtool/amtool 检查 → reload → 去页面确认生效。
四步缺一不可。"我改了"和"它生效了"是两件事，中间隔着一次 reload 和一次页面对照。

# 5.5　告警规则：全章最核心的语法

# 5.5.1　和记录规则的唯一区别

第 4 章讲过记录规则（record）。两者的结构几乎一样，只有一处本质区别：

记录规则告警规则
关键字recordalert
expr 返回值任意数值（求和、比率、耗时…）必须是布尔结果（真/假）
结果一条新时间序列一条告警（pending / firing）
用途别名 + 预计算决定是否告警

🧠 为什么必须是布尔？ 因为 Alertmanager 只关心"有没有告警"。
expr 返回 1，说明条件成立 → 告警；返回空（无结果），说明条件不成立 → 不告警。

注意：是"有结果/无结果"，不是"1/0"。 第 3 章讲过 > 80 是过滤语义——条件不成立时那条序列直接消失，所以表达式的"结果存在"就等于"条件成立"。

# 5.5.2　五个字段

groups:
  - name: flask_web                  # ① 告警组名
    rules:
      - alert: InstanceDown           # ② 告警名称
        expr: up{job="my_metric"} == 0  # ③ 条件表达式（布尔）
        for: 1m                       # ④ 持续多久才真正告警
        labels:                       # ⑤ 附加标签（路由依据）
          severity: critical
        annotations:                  # ⑥ 通知内容（人看的）
          summary: "Instance <!--swig￼0--> 停止工作"
          description: "<!--swig￼1--> job <!--swig￼2--> 已经停止1分钟以上"
          value: "<!--swig￼3-->"
字段必填说明
name（组）✅组名，在同一文件中需唯一
alert✅告警名称，要能一眼看出是什么问题（InstanceDown、HostOutOfDiskSpace）
expr✅PromQL 条件表达式，必须返回布尔结果
for❌（默认 0）条件成立后持续多久才真正告警。for: 0m = 立即告警
labels❌附加标签。⭐ 路由、抑制都靠它（severity 是最常用的一个）
annotations❌通知正文内容，支持模板变量

# 5.5.3　⭐ for 为什么必须有

for 解决的是**抖动（flapping）**问题。

假设规则是 内存可用率 < 10%，且 for: 0：

t=0s    内存可用率 9%   → 立即告警，发邮件
t=10s   某进程退出，可用率回到 40%  → 恢复，发恢复邮件
t=20s   进程又起来了，可用率回到 8% → 又告警，又发邮件

10 秒内你收到 3 封邮件，而实际上什么坏事都没发生。

加上 for: 2m 之后：

t=0s    9%    → Pending（还没告警）
t=1m    9%    → 仍在 Pending
t=2m    9%    → 持续满 2 分钟 → Firing，发邮件

✅ 这才是"真的有问题"。 短暂的内存尖峰不会吵醒你，长期不足才会。
for 的取值应当明显大于采集间隔（比如采集 15s，for 至少 1m），否则抖动过滤形同虚设。

💡 测试期的做法：上课/实验时为了不干等，把 for 改成 10s 甚至 0m。
但生产环境请老老实实按业务特性设 1m~10m，否则你会被自己的告警淹没。

# 5.5.4　三个状态：Inactive / Pending / Firing

stateDiagram-v2
    [*] --> Inactive
    Inactive --> Pending: 条件首次成立
    Pending --> Inactive: 条件恢复（未满 for）
    Pending --> Firing: 持续满足 for 时长
    Firing --> Inactive: 条件恢复（发 resolved）
状态含义是否发送通知
Inactive正常，条件不成立❌
Pending已触发阈值，但未满足 for 时长❌（还不发）
Firing已触发阈值且满足 for 时长✅ 发送

💡 排障时的用途：告警"卡在 Pending 一直不动"，说明条件在反复跳变（一会成立一会不成立），计数器一直被打断。这种情况要么 for 太长，要么表达式本身有问题。

# 5.5.5　模板变量

annotations 里可以引用告警上下文：

变量含义
{{ $labels.}}触发该告警的序列上某个标签的值
{{ $value }}触发时的样本值
{{ $externalLabels.}}全局外部标签
annotations:
  summary: "Instance <!--swig￼7--> 停止工作"
  description: "<!--swig￼8--> job <!--swig￼9--> 已经停止1分钟以上"
  value: "<!--swig￼10-->"

渲染出来长这样：

summary:     Instance 10.0.0.101:8000 停止工作
description: 10.0.0.101:8000 job my_metric 已经停止1分钟以上
value:       0

⚠️ 一个高频坑：模板里用了 {{ $alert.Annotations.value }}，但规则里没定义 value → 渲染出来是空的。
凡是模板里要用的 annotation，规则里必须先定义。 第 6 章会踩一次这个坑。

新手最大的困惑是："我知道要告警，但我不知道该监控什么、阈值设多少。"

答案是：不用你想，好心人早就写好了。

  • Awesome Prometheus Alerts：https://awesome-prometheus-alerts.grep.to/

它覆盖的规则数量惊人：

类别大致覆盖

数据库MySQL、PostgreSQL、Redis、MongoDB、Elasticsearch…

🎯 正确的学习姿势：先抄，再改，最后理解。

比自己拍脑袋想阈值高效十倍，也专业十倍。

# 5.5.7　主机规则节选（挑最典型的讲）

① 内存不足

- alert: HostOutOfMemory
  expr: node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes * 100 < 10
  for: 2m
  labels:
    severity: warning
  annotations:
    summary: "Host out of memory (instance <!--swig￼12-->)"
    description: "Node memory is filling up (< 10% left)\n VALUE = <!--swig￼13-->\n LABELS = <!--swig￼14-->"

🔗 看这条表达式：可用内存 / 总内存 * 100 < 10——正是第 3 章反复推导的那个公式！
这就是"基础概念 → 表达式 → 告警规则"的完整闭环。 你之前学的每一个运算，最终都落在这里。

② 磁盘空间不足（带 and 条件）

- alert: HostOutOfDiskSpace
  expr: (node_filesystem_avail_bytes * 100) / node_filesystem_size_bytes < 10
        and ON (instance, device, mountpoint) node_filesystem_readonly == 0
  for: 2m
  labels:
    severity: warning

💡 为什么要 and ... readonly == 0？
因为只读挂载的分区空间不会增长，属于"已知状态"，不该告警。这个 and 就是第 3 章的集合运算在实战里的用法。

③ CPU 负载高

- alert: HostHighCpuLoad
  expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[2m])) * 100) > 80
  for: 0m
  labels:
    severity: warning

⚠️ 课件原文这条表达式少了一对括号（100 - (avg(...) * 100 > 80），复制到生产会直接语法报错。照抄也要跑一遍 promtool check rules。

④ 网络带宽打满

- alert: HostNetworkInterfaceSaturated
  expr: (rate(node_network_receive_bytes_total{device!~"^tap.*|^vnet.*|^veth.*|^tun.*"}[1m])
       + rate(node_network_transmit_bytes_total{device!~"^tap.*|^vnet.*|^veth.*|^tun.*"}[1m]))
       / node_network_speed_bytes{device!~"^tap.*|^vnet.*|^veth.*|^tun.*"} > 0.8
  for: 1m
  labels:
    severity: warning

💡 device!~"^tap.*|^vnet.*|^veth.*|^tun.*" —— 排除虚拟网卡。这是"用正则排除噪声"的经典写法，第 3 章的 !~ 在这里发挥了实际价值。

⑤ 容量预测（趋势告警）

- alert: DiskWillFillIn12Hours
  expr: predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h], 12*3600) < 0
  for: 1m
  labels:
    severity: critical
  annotations:
    description: "Disk on <!--swig￼15--> will fill in approximately 12 hours."

🎯 这条是"高级感"最强的一条：不是等磁盘满了才告警，而是预测 12 小时后会满。
第 3 章讲的 predict_linear 就是为这个准备的。面试里能说出这条，直接拉开差距。

⑥ MySQL / blackbox 的例子（了解即可）

# MySQL 挂了
- alert: MysqlDown
  expr: mysql_up == 0
  for: 0m
  labels: { severity: critical }

# 连接数超过 80%
- alert: MysqlTooManyConnections
  expr: max_over_time(mysql_global_status_threads_connected[1m])
        / mysql_global_variables_max_connections * 100 > 80
  for: 2m
  labels: { severity: warning }

# HTTP 探测失败
- alert: BlackboxProbeFailed
  expr: probe_success == 0
  for: 0m
  labels: { severity: critical }

# HTTP 状态码异常
- alert: BlackboxProbeHttpFailure
  expr: probe_http_status_code <= 199 OR probe_http_status_code >= 400
  for: 0m
  labels: { severity: critical }

⚠️ 前提：这些指标得真的存在。没有 mysqld_exporter 就没有 mysql_up，表达式永远返回空，永不告警。
"告警规则写好了但从不触发"，第一件事就是去 Graph 页面验证表达式里那个指标到底有没有数据。（第 4 章的 absent() 就是用来兜这种情况的）

# 5.6.1　准备工作：开启 SMTP 授权码

# 5.7　告警静默（Silence）

# 5.7.1　什么时候用

最典型的场景：你要调试/维护，会反复重启服务。

你在改一个脚本 → 停服务 → 忘了改什么 → 再启动 → 又停 → ...
每一停，`up == 0` 就成立，告警就响，邮件就来。

但这不是"真故障"，是你自己造成的。这时候就该用静默。

🧠 静默 vs 抑制，别搞混：

  • 静默（Silence）：人工临时关掉某类告警（"我知道我在维护，别吵"）；
  • 抑制（Inhibition）：由规则自动让根因告警压制连带告警（"A 挂了，B 的告警不用说"）。

一个是"临时闭嘴"，一个是"逻辑降噪"。

# 5.7.2　Web 界面操作

Alertmanager UI → Silences → New Silence
  ├─ Matchers：填匹配条件（如 alertname=InstanceDown）
  ├─ Duration：静默时长（如 2h）
  ├─ Creator：谁建的
  └─ Comment：⭐ 为什么静默（必填，别偷懒）
→ Create

💡 Comment 一定要写清楚。三个月后你回来看"这条静默是谁为什么设的"，如果没有注释，你完全无从判断。
好的写法："2026-03-15 数据库升级维护，预计 2 小时，张三"。

# 5.7.3　恢复告警

Silences 列表 → 找到对应条目 → Expire

Expire = 让这条静默立即过期，告警恢复原样。

⚠️ 静默到期不会自动"补发"期间漏掉的告警。如果静默期内问题真的发生了，到期后告警会重新计算——所以静默时长要合理，别一设就是一天。

# 5.7.4　amtool 命令行方式（更适合自动化）

# 添加静默（2 小时）
amtool silence add alertname=InstanceDown \
  --duration=2h \
  --comment="数据库升级维护 - 张三" \
  --alertmanager.url=http://127.0.0.1:9093

# 查看当前所有静默
amtool silence query --alertmanager.url=http://127.0.0.1:9093

# 让某条静默立即过期
amtool silence expire <silence-id> --alertmanager.url=http://127.0.0.1:9093

💡 命令行方式的价值：可以写进变更脚本/发布流程里——"发布开始时自动静默，发布结束后自动解除"，比人工点鼠标可靠得多。

# 5.7.5　⭐ 一个容易被误解的点

静默只影响"发不发通知"，不影响告警本身的产生。

静默期间：告警照常 Inactive → Pending → Firing
         只是 Alertmanager 不往外发
静默解除：如果问题还在 → 立刻收到通知
         如果问题已解决 → 什么都不发

🧠 这个设计是对的：告警状态始终真实，只是"静音"了。

# 5.8　记录规则的两个补充参数

第 4 章讲了记录规则，这里补两个 groups 级别的参数（笔记 5.1 有提到，实战中很有用）：

groups:
  - name: custom_rules
    interval: 5s              # ⭐ 本组的计算间隔（默认继承 global.evaluation_interval）
    limit: 100                # ⭐ 本组最多生成多少条序列/告警（默认 0 = 不限）
    rules:
      - record: instance:node_cpu:avg_rate5m
        expr: 100 - avg(irate(node_cpu_seconds_total{job="node_exporter", mode="idle"}[5m])) by (instance) * 100
      - record: instance:node_memory_MemFree_percent
        expr: 100 - (100 * node_memory_MemFree_bytes / node_memory_MemTotal_bytes)
      - record: instance:root:node_filesystem_free_percent
        expr: 100 * node_filesystem_free_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}
参数作用典型用途
interval该组的计算周期关键指标算得勤一点（如 5s），冷门指标算得慢一点，省 CPU
limit产出上限⭐ 防止一条写错的规则把序列数打爆（如漏写 by 导致笛卡尔积）

💡 limit 是被严重低估的保护参数。 一条坏规则生成几十万条序列，能把 Prometheus 内存吃光。上线新规则前先给它加个 limit，是稳妥的做法。

# 5.10　面试高频问答

Q1：Prometheus 的告警是怎么实现的？

分两段。Prometheus 按 rule_files 里的告警规则，用 evaluation_interval 周期性地计算 expr；表达式有结果就说明条件成立，经过 for 指定的持续时间后状态变 Firing，然后把告警推给 Alertmanager。Alertmanager 负责去重、分组、抑制、静默、路由，最终通过邮件/企业微信/钉钉/Webhook 发出去。
关键点：Prometheus 只判断，Alertmanager 只通知，因为只有 Prometheus 手里有指标数据。

Q2：for 字段有什么用？

防抖动。条件刚成立时不立即告警，而是进入 Pending，持续满足 for 指定时长后才变 Firing 并发通知。这样可以过滤掉短暂的指标毛刺。
for 应当明显大于 scrape_interval，否则起不到作用。默认 0 表示立即告警。

Q3：告警有哪几个状态？

Inactive（正常）、Pending（已满足阈值但未达 for 时长，不发通知）、Firing（满足 for，已发送）。条件恢复后回到 Inactive 并发送 resolved 通知（需配置 send_resolved: true）。

Q4：group_wait、group_interval、repeat_interval 有什么区别？

group_wait：新告警组首次通知前等待多久，用来等聚合同组的其他告警。
group_interval：同一组告警有更新（如新增成员）时，多久再发一次。
repeat_interval：告警持续未恢复时，多久重复提醒一次。
三者配合实现"少发、发全、不遗漏"。repeat_interval 不能太小，否则会被邮件服务商封禁。

Q5：静默和抑制有什么区别？

静默是人工、临时地按标签暂停告警通知，常用于维护窗口，可在 Web 页面或 amtool 设置，到期自动失效。
抑制是规则自动行为：当源告警（根因）触发时，压制目标告警（连带故障），靠 source_match / target_match / equal 配置。

Q6：告警规则里 expr 能不能返回数字？

不能。expr 必须是布尔判断的结果。在 PromQL 里，比较运算符默认是过滤语义——条件成立时序列保留（有结果），不成立时序列消失（无结果）。Alertmanager 只关心"有没有告警"，所以"有没有结果"就是"要不要告警"。

Q7：写了告警规则，但从来没触发过，怎么查？

三步：① 把 expr 里的表达式贴到 Graph 页面，看有没有数据（指标不存在是首要嫌疑，可能没装对应 exporter）；② 看 Status → Rules，规则是否加载、状态是否 OK；③ 看是不是被 for 卡在 Pending（条件反复跳变）。
另外可以用 absent() 兜底，专门告警"指标消失了"这种场景。

□ 3. amtool check-config 通过
□ 4. systemctl restart alertmanager
□ 5. 停服务触发告警 → 收到【告警】邮件
□ 6. 恢复服务 → 收到【resolved】恢复邮件
□ 7. 对比两封邮件的差异（标题、状态）

思考题：send_resolved: false 时，第 6 步会怎样？

# 实验四　静默实战

□ 1. 继续停着 flask 服务，让告警持续
□ 2. Alertmanager → Silences → New Silence
     Matcher: alertname=InstanceDown
     Duration: 10m
     Comment: "实验维护"
□ 3. 观察：告警状态仍为 firing，但不再收到邮件
□ 4. 用 amtool 查看静默：amtool silence query
□ 5. Expire 掉静默 → 邮件立刻恢复

思考题：静默期间把服务恢复了，然后解除静默，会收到邮件吗？为什么？

# 实验五（进阶）　repeat_interval 实验

□ 1. 把 repeat_interval 设为 1m
□ 2. 保持服务停止 5 分钟
□ 3. 数一数收到几封邮件
□ 4. 改成 30s 再试一次
□ 5. 用这个实验向自己证明："生产环境绝对不能这么设"

# 5.12　下章预告

本章我们把告警"接通"了：规则能判断，Alertmanager 能发邮件。但它还非常"原始"：

  • 邮件正文全是英文的、格式难看；
  • 所有人收到同一个告警，不分轻重；
  • 一次故障触发 20 条告警，分不清哪条是根因。

下一章逐个解决：

问题解法
邮件难看告警模板（Go template + HTML 表格）
不分轻重告警路由（severity 分流 + 分级告警）
告警风暴告警抑制（根因压制连带）
只有邮件太单调企业微信、钉钉（含第三方 webhook 中转）
Alertmanager 单点Gossip 集群高可用

本章作业：把"七条必须带走的知识"抄到笔记里，并且不看文档写出一个带 for、labels、annotations 的完整告警规则，然后用 promtool check rules 验证通过。
