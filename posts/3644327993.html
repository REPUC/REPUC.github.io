# 自动化运维与 Ansible 概述

本文是 Ansible 系列的开篇，先建立整体认知：了解自动化运维要解决什么问题、运维工程师的核心职能与职业路线、企业真实的运行环境，以及 Ansible 是什么、为什么值得学。

# 一、自动化运维要解决什么

运维的核心工作可以概括为四类：平台架构组建（搭建）、日常运营保障（维护）、性能效率优化（调优）、DevOps 开发（趋势）。项目流程通常为：调研 → 计划 → 编码 → 打包 → 测试，再进入发布 → 部署 → 运维 → 监控 → 调优的循环。

随着服务器规模扩大，重复性的手工操作成为最大瓶颈。自动化运维的目标，就是用工具把重复工作固化下来，让运维干预降到最低，实现"自助服务"。正如《运维的未来》所言：

运维的未来是，让研发人员能够借助工具、自动化和流程，在运维干预极少的情况下部署和运营服务，从而实现自助服务。每个角色都应该努力使工作实现自动化。

Ansible 正是为此而生，其三大核心能力是：Ansible 模块、PlayBook 剧本、Roles 角色。

# 二、运维工程师的核心职能与工具生态

云计算运维工程师的工作围绕"重复性工作解决方案"展开，需要掌握一整条工具链：

领域代表工具
代码管理（SCM）GitHub、GitLab、BitBucket、SubVersion
构建工具Maven、Ant、Gradle
自动部署Capistrano、CodeDeploy
持续集成（CI）Jenkins、Travis
配置管理Ansible、SaltStack、Chef、Puppet
容器Docker、Podman、LXC
编排Kubernetes、Apache Mesos
服务注册与发现Zookeeper、etcd、Consul
脚本语言Python、Ruby、Shell
日志管理ELK、Logentries
系统监控Prometheus、Zabbix、Nagios、Graphite
性能监控AppDynamics、New Relic、Splunk
压力测试JMeter、BlazeMeter
Web 服务器Apache、Nginx
数据库MySQL、Oracle、PostgreSQL（关系型）；MongoDB、Redis（NoSQL）
项目管理Jira、Trello、Asana

其中配置管理是 Ansible 的核心舞台：它负责批量地配置和管理服务器，让成百上千台主机保持一致的状态。

# 三、运维职业发展路线

运维的进阶路径通常是：

基础运维 → 监控运维 → 系统运维 → 应用运维 → 自动化运维

  • 基础运维：负责基础设施的日常管理和维护，如服务器、网络设备、存储等。
  • 监控运维：设计、实施和维护监控系统，监测基础设施、系统和应用的性能与可用性。
  • 系统运维：管理操作系统（Linux/Windows 等）的安装、配置和维护。
  • 应用运维：管理应用程序和服务的部署、配置与性能优化。
  • 自动化运维：开发、实施和维护自动化工具与脚本，简化并自动化重复任务，提高效率。

越往高级走，对自动化能力的要求越高，而 Ansible 是进入自动化运维最主流、最易上手的入口。

# 四、企业实际运行环境

理解企业真实的环境分层，是做好自动化的前提。一套完整的环境通常包含：

  1. 开发环境：程序员个人办公电脑或项目的开发测试环境，部署开发软件，测试个人或项目整体的 BUG。管理者是程序员自己。
  2. 测试环境：测试工程师验证经过 Dev 环境测试通过的软件的功能与性能，判断是否达到预期并生成测试报告，管理者是运维。测试环境往往有多套，通常与产品线数量一致，满足多版本并发测试即可，不宜过多。
  3. 预发布环境：由运维管理，使用与生产环境一致的数据库、缓存等配置，在上线前验证是否正常。
  4. 发布环境：包括代码发布机（有些公司为堡垒机，作为安全屏障），由有经验的运维管理，负责将代码发布至生产环境。发布机通常需要两台（主备）。
  5. 生产环境：对用户提供服务，管理者只能是运维。服务器数量多、应用重要，往往需要自动化工具协助部署配置。
  6. 灰度环境：属于生产环境的一部分。在全量发布前，将功能面向少量精准用户发布。例如共 100 台生产服务器，先发布其中 10 台，这 10 台就是灰度服务器。当版本功能变更较大时，先让部分用户体验，确认无重大问题后再全量发布。

# 五、程序发布与灰度发布

程序发布有两条硬性要求：不能导致系统故障或完全不可用，不能影响用户体验。

预发布验证：新版本代码先发布到与线上配置完全相同、但未接入调度器的服务器上验证。

灰度发布可基于主机、用户或业务维度进行。一种常见的发布路径是用软链接切换版本：

软链接:  /webapp/xxx        -> 指向新版本真实目录
OLD 真实目录: /webapp/xxx-1.1
NEW 真实目录: /webapp/xxx-1.2

发布过程：

  1. 在调度器上将一批主机下线（标记为 maintenance 状态）；
  2. 关闭服务；
  3. 部署新版本应用程序；
  4. 启动服务；
  5. 在调度器上重新启用这一批服务器。

自动化灰度发布可以通过脚本或发布平台实现，后续可基于 Jenkins 等工具自动化完成。

# 六、自动化运维的应用场景

借助 Ansible 的主机清单功能，可按业务需求将服务器划分为不同组（主机分类），典型应用场景包括：

  • 文件传输：批量分发文件、配置、密钥；
  • 应用部署：批量安装、部署应用；
  • 配置管理：统一维护系统配置，保持主机状态一致；
  • 任务流编排：按顺序编排多步骤任务，实现复杂部署流程。

# 七、常用自动化运维工具对比

工具语言特点
AnsiblePythonAgentless，无需安装 Agent，适合中小型应用环境
SaltstackPython一般需部署 Agent，执行效率更高
PuppetRuby功能强大、配置复杂、重型，适合大型环境
FabricPythonAgentless
ChefRuby国内应用较少
Cfengine / func—较早的配置管理工具

Ansible 最大的优势是Agentless（无代理）：只需主控端安装 Ansible，被控端只要有 Python 和 SSH 即可，无需在每台机器上部署 Agent，部署和维护成本极低。这也是它成为最流行配置管理工具的关键原因。

# 八、Ansible 介绍

# 8.1 发展史

  • Ansible 官网：https://www.ansible.com/ ，作者 Michael DeHaan（同时也是 Cobbler 与 Func 的作者）。
  • 名称源自科幻小说《安德的游戏》中跨越时空的即时通信工具，寓意可远程实时控制远方舰队。
  • 2012-03-09 发布 0.0.1 版；2015-10-17 Red Hat 宣布以 1.5 亿美元收购 Ansible。
  • 官方文档：https://docs.ansible.com/

开源项目的商业化价值值得参考：以国人编写的开源项目 JumpServer 为例，后来被飞致云收购，为双方都带来了巨大商业价值。学习 Ansible 这样的主流开源工具是值得投入的。

# 8.2 Ansible 功能

  • 批量执行远程命令：对远程多台主机同时执行命令；
  • 批量安装和配置软件服务：以自动化方式配置和管理各种服务；
  • 编排高级企业级复杂 IT 架构任务：通过 Playbook 和 Role 轻松实现大型复杂架构；
  • 提供自动化运维开发 API：许多运维工具（如 JumpServer）基于 Ansible 实现自动化管理功能。

# 8.3 Ansible 特性

  • 模块化：调用特定模块完成特定任务，支持自定义模块，可用任何语言编写；
  • 关键依赖：Paramiko（Python 对 SSH 的实现）、PyYAML、Jinja2（模板语言）；
  • 基于 Python：实现简洁，生态丰富；
  • 部署简单、Agentless：基于 Python 和 SSH（默认已安装），无需代理、不依赖 PKI（无需 SSL）；
  • 安全：基于 OpenSSH；
  • 幂等性：一个任务执行 1 遍和执行 n 遍效果一样，不因重复执行带来意外（Shell 脚本实现幂等性很困难，这是 Ansible 的显著优势，但注意此特性并非绝对）；
  • 支持 PlayBook 编排：YAML 格式，支持分支、循环、判断、变量等丰富数据结构；
  • 强大的 Role 角色：多层解决方案，便于复用与组织。

# 8.4 Ansible 架构

组成：Ansible 命令工具是核心执行工具，组合以下四部分：

  • INVENTORY：Ansible 管理的主机清单（默认 /etc/ansible/hosts）；
  • MODULES：执行命令的功能模块，多数为内置核心模块，也可自定义；
  • PLUGINS：模块功能的补充，如连接类型插件、循环插件、变量插件、过滤插件等；
  • API：供第三方程序调用的应用程序编程接口。

命令执行来源：

  • USER（系统管理员）直接执行；
  • PLAYBOOKS（任务剧本，由 Ansible 顺序执行的 YAML 配置文件）；
  • CMDB（配置管理数据库）API 调用；
  • 公有云/私有云 API 调用。

调用关系：USER → Ansible Playbook → Ansible。

注意事项：

  • 执行 Ansible 的主机一般称为管理端/主控端/中控/master/堡垒机；
  • 主控端 Python 版本需 2.6 或以上；
  • 被控端 Python 版本小于 2.4 时，需安装 python-simplejson；
  • 被控端如开启 SELinux，需安装 libselinux-python；
  • Windows 不能作为主控端，但可以做被控端。

# 小结

本文梳理了自动化运维的全貌：运维的职能与工具生态、职业发展路线、企业分层环境、发布与灰度流程，以及 Ansible 的发展史、功能、特性与架构。Ansible 凭借无代理、基于 SSH、幂等、模块化、Playbook 编排等特性，成为自动化运维的主流选择。下一篇我们将进入实操：如何安装 Ansible、配置主机清单。
